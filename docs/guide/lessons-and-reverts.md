## Lessons

A lesson is one sentence a model writes from a reply a person wrote under one of the reviewer's findings, when the reply showed that the finding was wrong. Later reviews of that repository are shown it as data for 90 days, so that they leave out a finding of the kind it says was wrong. Lessons are made and shown only with `learning: true`. **What lessons do to findings and to the score is not measured:** the evals can show a lesson (see [Measuring lessons](#measuring-lessons)), but the measurement has not been run on a deployment's data.

What an operator must know:

- **What is judged, when, and what it costs.** Every reply a person wrote in a thread that one of the reviewer's findings started, of any severity, each judged alone against its finding; a reply under an inline note is not judged. Once in a UTC day, at the first tick of the five-minute timer after 00:00 UTC, a run takes the replies written in the 90 days before that 00:00 that have no classification yet, those of people with access first, then the oldest, so a reply that is 90 days old is never judged. One model call for a reply, and one more when the answer is no verdict, with the review model, its client, `model.toolChoice` and the time limit a review's request has (`model.timeoutSeconds`). At most 100 replies a run, and of those at most 20 from accounts with no access to the repository (`JUDGE_STRANGERS` in [src/shell/judge.ts](../../src/shell/judge.ts)): the rest of such replies wait. A run that does not complete (a stop, the daily limit, a paused model, three failures at the provider in a row, a failing database) keeps what it wrote and is tried again an hour later, or at the first tick after a restart, and takes up to 100 replies again; a restart after a run that completed starts none that day. What the model's provider is sent: the file's name when it may be shown, the finding's severity, the finding's text and the reply's own words, 2,000 characters of each of the two texts, between data markers with a token made for that call. What a reply quotes from someone else (its quoted lines, and its `<blockquote>` and `<details>` blocks) and its fenced code blocks are left out, so a reply that only quotes is not sent, and "agreed" under a quote teaches nothing; an indented code block, `<pre>`, a table and an html comment stay in. No code and no login. A request is about 2,400 tokens of input by the service's estimate, and one asked again about 3,100; that counts the service's own requests: the client's one wait on a rate limit and its fallback models can add requests to each. The cost counts in `limits.spendPerDay`, at the start of its day; a cost the endpoint did not report raises `cost_unknown`, as for a review. The judge makes no call while reviews are paused, for the daily limit or for the model's key: the run ends for now. It runs in dry run too, and is paid for.
- **Who makes a lesson.** A person the git service reported, when they wrote, as owner, member or collaborator of the repository, the pull request's author included. Never a stranger: a stranger's reply is judged, its verdict is stored, and it makes no lesson. Never a bot: a bot's comments are not stored.
- **The guards, each with its outcome code.** Each judged reply has a row in `visto_ai.reply_verdicts` with its classification (`confirmed_fix`, `valid_pushback`, `invalid_pushback`, `question` or `noise`) and an outcome. `lesson`: a lesson was made. `none`: the classification is not `valid_pushback`. `no_rule`: the judge gave no lesson. `no_access`: the writer is a stranger. `not_printable`: the finding's file has a name that is never shown. `no_quote`: the judge quoted nothing, or under 15 or over 200 characters. `quote_not_in_reply`: the quote is not in the writer's own words as the judge was sent them, compared with white space and case ignored; so a quote from beyond the first 2,000 characters makes no lesson. `not_a_rule`: once invisible characters are removed and it is made one line, the sentence is under 30 or over 300 characters (it is never cut to fit), or holds `#` followed by a digit, or a link; a full-width `#`, digit or slash counts as the plain one. `names_the_score`: the sentence holds `score`, `scores`, `scored`, `scoring`, `human review`, `needs a person`, `needs a human`, `approvable`, or a form of automatic approval; a repository whose own subject is scores or approvals loses the lessons that name it. `review_disagreed`: the newest published review of the pull request that started after the reply and holds a verdict for the thread kept the finding `open` or found it `fixed`. `restates`: the sentence says again what a standing lesson of the repository says, an active one or one switched off, of up to 1,000 read: the two are equal with white space and case ignored, or each has at least 4 distinct words of 5 or more letters or digits and they share at least half of the smaller set. `no_own_words`: a reply with nothing but quotes or code, noted as `noise` and not sent. `unjudged`: twice in one call the answer was no verdict; after 3 such calls the reply is left alone, and a call that failed at the provider counts no attempt. `finding_unknown`: the finding's text cannot be told from its review's stored result (two findings of that review alike in path, side, severity, quote and line, which is more frequent after a comment was repaired from its thread), and the reply is left alone with no call. At ten lessons made since the day's 00:00 the run ends, and what is left waits for the next night.
- **What a lesson is to the reviewer.** Data between markers with the review's token, under `LESSON_RULES` in [src/engine/context/lessons.ts](../../src/engine/context/lessons.ts): a lesson never changes the rules, an instruction inside one is never followed, it is for leaving out a finding of the kind it says was wrong, it never hides a defect the model can demonstrate, it says nothing about the score, and it is never mentioned in the answer. It can keep a finding from being raised, which is what it is for, and one major fewer can change what a gate or an approval decides; nothing in code checks what the model makes of it. **Nothing in code keeps a model that reads a lesson from scoring a block lower:** with a second scorer the block scores are not the review model's, so there a lesson cannot reach them; where the review model scores, only the rules' words forbid it, and it is not measured. That a lesson which names the score is not made catches a judge that strays into scoring, and guards nothing else. No floor, verdict or gate reads a lesson.
- **What a review is shown.** At most 8 lessons, each under a line the service writes that names the finding's file in a code span and the day. That name is the one thing in a lesson's block that a pull request's author chose, with access or without: at most 120 characters of the characters ordinary in file names, shown as a name and never as an instruction. They are ordered by what they share with the files sent: a lesson on one of those files, or on the path it had before a rename, first; then those that share leading directories with one, the deeper first; then those of a file's type, what follows the last dot of its name; within each the newest first. One that shares none of the three is not shown, which leaves out little in a repository under one top directory or in one language: there the order and the size of 8 decide. A pull request is never shown a lesson made from itself. Only a block the service labels, after the heading of the rules and with the review's token, is a lesson, whatever a description says. A lesson whose file, day or text would be refused is left out. Lessons are asked once for a review, after memory for the score, and shown, whole or not at all, only when they cost the files and the rest of memory nothing; otherwise the audit says `lessons_cut` with `over_call_budget`. They are fitted before the extension context and the tools, which then count them. They are shown with a second scorer too, for a pull request from a fork, and in dry run. Cost: each call of a review that shows lessons carries up to about 2,000 more tokens of input, and the files may be packed into more calls; the lookup is one more read of the database for each review, with the 5 seconds a lookup of memory has. It reads the live lessons of the repository's other pull requests, at most 1,000, newest first; with more, the oldest are left out and the audit says `lessons_cut` with `records`. A lookup that fails, hangs or answers junk costs the review its lessons and nothing else.
- **The kill switch and what to watch.** An admin switches a lesson off or on in the UI's Memory screen (see [Memory](memory.md) and [The UI](the-ui.md)), or in the database.

```sql
-- the active lessons of one repository; a review is shown those whose created_at has passed
select id, number, created_at, expires_at, path, lesson, excerpt
from visto_ai.memory_records
where owner = 'acme' and repo = 'shop' and kind = 'lesson' and status = 'active' and expires_at > now()
order by created_at desc;
-- switch one off: it is in no review from the next one on, and the judge will not make it again while it stands
update visto_ai.memory_records set status = 'disabled' where id = 42;
-- what the judge made of the replies
select outcome, count(*) from visto_ai.reply_verdicts where owner = 'acme' and repo = 'shop' group by outcome order by 2 desc;
-- replies under a comment the service does not hold: one of the reviewer's that was not stored, one of another bot
-- (never stored), or a person's from before the service received webhooks. The three cannot be told apart here, so the
-- count is an upper bound on the replies to the reviewer that are never judged for want of their finding
select count(*) from visto_ai.human_activity h
where h.kind = 'inline_comment' and h.reply_to is not null
  and not exists (select 1 from visto_ai.human_activity p where p.service = h.service and p.kind = 'inline_comment' and p.source_id = h.reply_to)
  and not exists (select 1 from visto_ai.review_comments c where c.service = h.service and c.comment_id = h.reply_to);
-- let a reply the judge gave no verdict for be judged again; a reply whose finding cannot be read (finding_unknown)
-- is left out, since the next run would retire it again with no call
update visto_ai.reply_verdicts set attempts = 0 where reply = '1234567' and classification is null and outcome = 'unjudged';
-- what the judge cost, by repository and day; each row of judge_calls holds the pull request and the reply it was for
select owner, repo, date_trunc('day', at) as day, sum(calls) as calls, sum(cost) as cost
from visto_ai.judge_calls group by 1, 2, 3 order by 3 desc, 1, 2;
```

  A lesson stands while it is active or switched off and has not expired. The quote, `excerpt`, is the words of the reply the judge quoted, at most 200 characters; it is stored, shown by no screen and never sent to a review.
- **A judge that runs and teaches nothing.** The start's `lessons_state` line and each run's `lessons` line show replies judged beside lessons made, and the outcomes above say why each reply made none. Many `no_access` verdicts over weeks usually mean that the git service reports the writers as having no access to the repository, as it may for a member whose membership is private.
- **The records of a review and of a run.** `review_runs.result` holds `dependencies.memory.lessons` when the memory has lessons and the review got as far as asking for them: a state, a short code and the number of lessons shown. `ok` with `ok`; `empty` with `no_lessons`; `skipped` with `no_model_call` (the review called no model) or `no_room`; `error` with `timeout`, `lookup_failed`, `bad_answer`, or the short code the lookup failed with. The audit names each lesson shown (`lesson_shown`, with its source reference and `file`, `directory` or `type`), each cut (`lessons_cut`, with `lessons`, `fields`, `names`, `texts` or `records`, and with `lessons` and `over_call_budget` when they did not fit) and a failure (`lessons_failed`). The `review` log line's `memory` carries `lessons` with the same three fields when the result has it. The alerts `memory_error` and `memory_ok` hear both parts: a review that records `error` in either is a failure, with the code of the first part in error; else one that records `ok` or `empty` in either is a success. The nightly work logs `lessons_state` at start (when the work began, when a run last completed, and its totals); `lessons` after each run, also one that found nothing, with its counts, its cost, `more` when it ended with replies unfinished, and `end`: `done`, `lesson_cap`, `stopped`, `spend_limit`, `model_error`, or a provider's `auth`, `no_credit`, `rate_limited`, `timeout` or `provider`; and `lessons_failed` with a short code when a run failed, or when a tick's read of the row failed or took more than 5 seconds (`timeout`). No line holds a reply's words, a lesson's text, a quote, a path or a login. The table `visto_ai.learning` holds a second row, `lessons`: when it was made, when a run last completed (`done` or `lesson_cap`), and running totals of replies classified, lessons made, replies left alone, and calls that failed at the provider or gave no verdict. A run that does not complete adds its counts and not its time; a stopped run adds nothing, since the database may be closing. The alert `lessons_stale` (with `hours`) is raised when no run has completed for 36 hours: it is checked at every tick of the five-minute timer, once the row is read or its read has failed, and counts from the row's last run, or from when the row was made, or, when the row is missing or cannot be read, from the last run this process completed or from its start. It is raised once until a run completes.
- **A stop.** A run under way is told, starts no further call, asks no second time for a reply whose first answer was no verdict, and sends the database nothing more; the stop waits for it at most 5 seconds before the database closes. A call answered after the stop is in the run's line and the spend guard is told of it, but nothing is written for it: its reply is judged again, and its cost is in no sum.
- **What is not followed.** A reply edited or deleted later: a lesson made from it stays until it is switched off or expires. A lesson that is confirmed again is not renewed. Two lessons that disagree both stand. A stored result that lists one comment twice among its thread verdicts gives the veto one of the two. Two services running the judge at once on one database would write its cost twice; one service runs one judge, and a second instance stops at once.
- **The migration.** Lessons add one migration, `0011_lessons`: the tables `reply_verdicts` and `judge_calls`, and on `memory_records` a column for a lesson's text. It is applied whether or not learning is on. A previous release refuses to start on a database that has it. `eval:seed-memory` now ends with `database_not_migrated` on a database that has not had it, where it asked for `0010_memory`.

## Measuring lessons

The evals can be shown lessons as of each case. The lessons they are shown are made by the eval, from an export of a deployment's findings and the replies under them, and not read from the deployment's own records. **Nothing here has been run on a deployment's data yet, so what a lesson does to findings and to the score is still not measured.** What follows is how to measure it, step by step, and what the measurement cannot show.

What an operator must know:

- **The export, and who runs it.** Only the person who runs the deployment can make it, since it is the one command here that connects to a database:

```bash
npm run eval:export-findings -- --config config.local.yml --out ../export.jsonl
```

  It reads in one read-only transaction and writes nothing to the database. It refuses a database that has not had migration `0003_publishing` (`database_not_migrated`) and an `--out` that already exists unless `--force` is given (`out_exists`). The file must be outside the project folder, and it is written mode 600. It holds, for every finding comment of a published run (not a note): the run's id, head, base and start; the finding's text; every inline comment that replies to it, with its writer's association with the repository; and every later published run of the pull request that kept a verdict for the thread. It holds no login, no title, no description and no record of memory. It is private: it holds finding texts and replies, and nobody but the operator should hand it on without reading it. It prints `findings <n>, with replies <n>, replies <n>, pull requests <n>`.
- **The history file of the same window.** `eval:import-history` (see [Backtest](backtest.md)) over the same repository and the same dates. The export holds no description and no branch, and the replay cases need them; a pull request that is not in the history file gets no case. The history file holds merged pull requests only.
- **The judge of replies.** `eval:judge-replies` asks the model again for every reply in the export, with the code the service's nightly judge uses, and runs the service's nights over the export: each 00:00 UTC from the day after the earliest reply up to the 00:00 of the export's day, as if learning had been on from the first reply. The deployment's own lessons and verdicts are not read, and the judge does not answer as it did at night, so the lessons made are the eval's, not the deployment's.

```bash
npm run eval:judge-replies -- --findings ../export.jsonl --config config.local.yml --out ../lessons --max-cost 2
```

  It makes paid model calls, one for each reply and one more for an answer with no verdict, with the review model, `model.toolChoice` and `model.timeoutSeconds` of the config. `--max-cost` is 2 USD by default and counts only what that run spends. It needs no `GITHUB_TOKEN`. It writes `lessons.json` (mode 600) and `summary.md` (counts only) in `--out`, and `answers.jsonl` (mode 600). **Every answer is kept** in `answers.jsonl`, keyed by the reply, the attempt, the model, its fallbacks, the tool choice and the judge's input, so a second run asks only what is not kept, and a changed rule, finding text, reply, model, fallback or tool choice asks the affected replies again. A failure at the provider is never kept. It prints `nights <n>, judged <n>, lessons <n>, given up <n>, waiting <n>, calls <n>, asked now <n>, cost <n>, spent now <n>`, and `stopped: <reason>` when the run did not finish.
- **A run that is cut is refused.** A night that ended for any reason but `done` or the lesson cap, or in which a call failed at the provider, or a run stopped by `--max-cost`, stops the simulation and writes `lessons.json` with `complete: false`. `lesson-cases`, `replay`, `backtest` and `memory-count` refuse it with `lessons_incomplete`. Run the command again with the same `--out`: it pays only for what is not kept. A lessons file that does not parse is `bad_lessons_file`.
- **A lesson is live from the night that made it.** A review at a date is shown the lessons made at or before that date, from the 00:00 after their reply, and not yet expired (90 days). A later verdict counts at a night only when its run started after the reply and was published before that night. A case is never shown a lesson made from a reply on its own pull request, nor one made from a reply written on its own day.
- **The cases, and the count.** `eval:lesson-cases` joins the export, the lessons file and the history file, calls no model and reads no network, and writes the replay's case file:

```bash
npm run eval:lesson-cases -- --history ../history.jsonl --findings ../export.jsonl --lessons ../lessons/lessons.json --out ../lesson-cases.jsonl
```

  It refuses a lessons file made from another export (`different_export`) and an existing `--out` without `--force` (`out_exists`); the case file is written mode 600. It prints `cases <n>, labels valid <n> invalid <n>, cases shown a lesson <n>, invalid labels in them <n>, skipped not in history <n>, no base <n>, same head <n>`, then a line `<key>: lessons <n>, invalid <n>, valid <n>` for each case. `--only-shown` writes only the cases the count says would be shown a lesson. One case is made for each published run of a pull request the history file holds, with at least one labelled finding, at the run's head, against its base, dated by the run's start (`review_at`). Its title, description, branches and author are the history file's, found by repository (compared in lower case) and number. A run with no base is skipped (`no_base`), and a second run at a head that already made a case is skipped (`same_head`). The case is reviewed whole at the run's head, though the run itself may have been an incremental review.
- **The labels.** The first decisive reply, in time order, by a person with access labels the finding: `valid_pushback` makes it `invalid`; `confirmed_fix` and `invalid_pushback` make it `valid`. With no decisive reply, the newest later verdict of the thread is read, whatever its time: `fixed` makes it `valid`. Anything else gives no label. A label carries the comment's id, path, side, line and severity, and no text. A label is a model's reading of a reply and not a person's; a stranger's reply labels nothing. The judge that makes lessons also makes the labels, but a case is never shown the lesson made from the reply that labelled it.
- **The floors, before any paid run.** The count says how many cases would be shown a lesson, and how many `invalid` labels are in them, with the history file's final files standing for the files the review is handed, so it can be off by the files that changed between the run's head and the merge. A paid replay is worth making only with at least 20 cases shown a lesson and 10 `invalid` labels in them; a paid backtest, with at least 20 cases shown a lesson (`eval:memory-count --lessons`, below) and 10 labelled files. These are starting values, as the memory count's were, and not a finding. With fewer, a paid run cannot show anything, whatever lessons do.
- **The four runs.** Two baselines (no lessons), two candidates (with them), each pair on the same file and config, so that the noise between two identical runs is known:

```bash
npm run eval:replay -- --cases ../lesson-cases.jsonl --out ../runs/off-1 --label off-1 --config config.local.yml
npm run eval:replay -- --cases ../lesson-cases.jsonl --out ../runs/off-2 --label off-2 --config config.local.yml
npm run eval:replay -- --cases ../lesson-cases.jsonl --lessons ../lessons/lessons.json --out ../runs/on-1 --label on-1 --config config.local.yml
npm run eval:compare -- ../runs/off-1/summary.json ../runs/on-1/summary.json --noise ../runs/off-2/summary.json
```

  The same four runs are made on the history file with `eval:backtest` and `--lessons`, and compared with `eval:score-compare` (see [Backtest](backtest.md)). A difference smaller than the noise between the two baselines is no finding, and "no measurable effect" may mean "too few cases".
- **What the eval cannot show.**
  - The lessons are the eval's, made by a judge that does not answer as it did at night; a deployment's own lessons are not these.
  - The eval cannot tell a lesson a team switched off. One a team rejected in the deployment is shown in the eval, which can only make lessons look worse than they are.
  - The service runs a night at the first tick after 00:00, or an hour or more later after a retry or an outage; the eval runs it at 00:00. A review that starts in between is shown a lesson in the eval that the service had not made yet.
  - The replay is shown lessons alone: its memory holds no signal and no revert, and its results hold no block scores. What a lesson does to the score is seen only in the backtest, on the history file's pull requests.
  - A finding whose text cannot be told is exported with no text and the judge gives no verdict for it (`finding_unknown`).
  - Neither comparison can tell a lesson that changed a finding from noise on a small count.
- **What is printed and what is not.** The commands print counts, costs and short codes. No reply, finding, lesson text, quote, path or login is printed or logged, and `summary.md` holds none. A file that cannot be read is named by its line number only (`bad_findings_line_<n>`, `bad_answers_line_<n>`). `export-findings`, `judge-replies` and `lesson-cases` need no `GITHUB_TOKEN`, and every file they read or write must be outside the project folder.

## Reverts

A revert is a merged pull request whose description starts with the line GitHub's revert button writes. With learning on, the files of the pull request it reverted are recorded, and later reviews of that repository are told that a change to such a file was reverted, as context for the score. **What a reverted line does to the score is not measured.**

What an operator must know:

- **What a revert is.** A merged pull request whose description's first line that is not blank is, exactly as it is written, `Reverts <owner>/<name>#<number>`: the line GitHub's revert button writes, naming the pull request's own repository, with nothing after the number but spaces and tabs. Only the first 4,000 characters of a description are read; in a longer one, a line that runs to the cut names nothing, since the cut may have shortened it. Nothing is stripped before the line is read, and every line end a renderer honours ends the line: a carriage return alone, the Unicode line and paragraph separators, the next-line character, a form feed and a vertical tab, beside the line feed. The number is read from every event of a pull request that is not merged, and from the delivery of its merge, and stored with the pull request, whether or not learning is on. Nothing else of a description is stored, logged or sent.
- **What is not one.** A revert made on the command line, whose reference is in a commit message; the short form `Reverts #12`; a reference below another line, a sentence or a template, or inside an HTML comment, a collapsed `<details>` block, a code block or a quote; a space before the word; a reason, a period or any other character after the number on its line; an invisible character anywhere in the line, or alone on a line before it; a reference to another repository, or to a number no pull request can have; a line added after the merge, whatever order the deliveries arrive in: once a pull request is merged, only the delivery of its merge sets the number; a reference to a repository by a name it had before a rename.
- **What is recorded, and when.** With learning on, by the five-minute pass, when the merge of the reverting pull request is stored; the delivery of the merge wakes the pass. One record of the kind `revert` for each path of the reverted pull request's last review, which is its newest completed run, a dry run included, whose stored list of files is not empty: a renamed file under both of its paths, at most 300 paths in the stored order, and none for a path that is never shown. Each is dated by the merge of the revert and expires 180 days after. The pass logs one `revert` line for each revert it looks at, with the two numbers, a code, `files` (the records made), `added` (the rows added now) and `cut` (the paths the limit of 300 left out); the records count in the pass's `added` and in the row `signals` of `visto_ai.learning`. The codes: `recorded`; `not_stored`, the pull request named is not stored; `not_merged`, it is not stored as merged, or was merged after the revert; `same`, the pull request names itself; `no_files`, the pull request named has no such run. In the last four nothing is recorded, and the reverting pull request is marked as looked at like any other. So a revert looked at before the merge of the pull request it names was stored, as after an outage whose deliveries were sent again in another order, records nothing then. The pass looks at the reverting pull request again when an inline comment on it is stored after that look, from any account that is not a bot, a stranger's and its author's included, or once the last statement below is run. A look again writes its line again: with `added: 0` when its records are there, or with the records it now makes when the pull request it names is now stored as merged with a review. Two passes at the same moment can each log the line, and each record is written once.
- **Who can cause one.** Whoever writes the first line of a description, a stranger on a fork included, once a person with write access merges the pull request. The line that counts is the one shown at the top of the pull request, as it is written, so it names the number the person who merges sees. With auto-merge or a merge queue, the author can still change that line after a person with access enabled the merge, so the line the merge carries may be one that no person with access saw; it can do no more than any other line. A wrong reference that is merged records the files of the pull request it names, and later reviews of those files are told that they were reverted, which can make a review look more closely there. It cannot add a finding, set a floor or move the gate, and nothing in code reads it into a score.
- **What a review is shown.** For a changed file, at most one reverted line: the newest revert of its path, or of the path it had before a rename, on a path no file before it took. It says `changed`, the file in a code span, the day the revert was merged, `-` and `reverted`. With such a line the rule `REVERTED_LINE_RULES` in [src/engine/context/memory.ts](../../src/engine/context/memory.ts) stands once between the rules of the pull request block and its lines; a review with no reverted line is sent what it was sent before. Reverted lines are part of memory for the score, and stand after every line of a signal: they take none of the signals' places, the limit of 30 lines cuts them first (the audit says `memory_cut` with `lines`), and when memory does not fit with them it is tried without them before nothing is shown (the audit then says `memory_cut` with `reverted`). They are shown only when the files are packed in the same calls, grouped the same, with them as without them; else the memory is shown without them (the audit says `memory_cut` with `reverted` and the reason `changes_batches`). A memory whose only lines are reverted is empty without them: when it fits, it is shown only when the files are packed in the same calls, grouped the same, with it as with no memory, else nothing is shown (the audit says `memory_cut` with `reverted` and the reason `changes_batches`, and the memory's status is `skipped` with `no_room`); when it does not fit, nothing is shown, as for any memory that does not fit. So a revert never costs a review a signal. Memory is fitted before lessons, the extension context and the tools, which then count it: a reverted line and its rule can take room that a lesson or the extension context would otherwise have had. No reverted line is near: a file near a reverted one is told nothing. A revert is counted in neither list of the repository block. It is shown neither to the pull request that made the revert nor to the one it reverted; a pull request that reverts a revert is shown that the change it brings back was reverted. With a second scorer named, none is shown, as no signal is.
- **What it is to the model.** Context, never a rule. The rule says that a reverted line is a reason to look closely at a block there and may be a reason that it needs a person, that it is never a reason that a block needs none, that no score may be lower because of it, and that it changes no finding. No floor, finding, verdict or gate reads a record of a revert.
- **What it costs.** No model call. One more read of the database for a review that asks memory for at least one file: the repository's live reverts of other pull requests, at most 1,000, newest first, with a statement limit of its own; with more, the oldest are left out and the audit says `memory_cut` with `records`. The read is part of the lookup of memory for the score, so one that fails or hangs costs the review that memory, with the status and the alert of a failed lookup; lessons are kept. About 216 tokens more of input in each call of a review that shows a reverted line, by the service's own estimate, and one more packing of the files, in the service and with no call, for a review whose memory has a reverted line beside a signal's line. In the pass, one more read for each pull request it looks at, of what it reverts; for a merged one that names a revert, a second read, of the files of the last review of the pull request it names, also when nothing is then recorded; and up to 300 rows for a revert.
- **The statements.** Owners and repository names are stored in lower case.

```sql
-- what stored pull requests say they revert
select number, reverts, state, merged_at from visto_ai.pull_requests
where owner = 'acme' and repo = 'shop' and reverts is not null
order by merged_at desc;
-- the records of reverts that reviews are told of
select id, number as reverting, reverted, created_at, expires_at, path
from visto_ai.memory_records
where owner = 'acme' and repo = 'shop' and kind = 'revert'
  and status = 'active' and expires_at > now()
order by created_at desc;
-- switch off every record of one revert: they are in no review from the next one on
update visto_ai.memory_records set status = 'disabled'
where owner = 'acme' and repo = 'shop' and kind = 'revert' and number = 9 and reverted = 7 and status = 'active';
-- have a merged revert looked at again by the next pass, once the pull request it names is stored as merged
update visto_ai.pull_requests set learned_at = null, learn_attempts = 0
where owner = 'acme' and repo = 'shop' and number = 9;
```

- **What was checked against GitHub.** The line was read from the descriptions of pull requests that the revert button opened in public repositories: the whole description is that one line, with the repository's full name, and the page shows it as a short link. Two other merged reverts read there had a description written by hand or on the command line, and name nothing under this rule. A repository renamed since keeps its old name in such a line, which then names nothing. No revert was made on a repository the app is installed on, so that the delivery of a merge carries the line is not verified.
- **The migration.** Reverts add one migration, `0012_reverts`: a column `reverts` on `pull_requests` and a column `reverted` on `memory_records`. It is applied whether or not learning is on. A previous release refuses to start on a database that has it, and it cannot be put back. `eval:seed-memory` now ends with `database_not_migrated` on a database that has not had it, where it asked for `0011_lessons`. A pull request merged before the upgrade has no number stored, and is not read as a revert.
