---
title: Leave dry run
description: "Set `dryRun: false` in the config."
---

Set `dryRun: false` in the config. A config that does not write `dryRun` runs in dry run: the service posts only when the key says `false`. Nothing else changes: from then on the service writes to GitHub, so check the app's permissions first (see [Creating the app](create-the-github-app.md)).

Extension modules are asked for context in dry run too; from the switch on, their notifiers are told of each published review and their sinks of each alert (see [Extensions](extension-modules.md)).

Nothing is posted at the switch itself. A review recorded in dry run is never posted; each open pull request gets its review at its next event (a push, a reopening, a `/review`). Jobs that were waiting run as before and now post, and after a stop the deliveries GitHub could not make (at most 200) are asked for again, so the pull requests they name are reviewed and posted.

- **Posting.** Each review is posted once, as a comment review pinned to the commit it was computed for, with its inline comments; with automatic approval on, as an approval when every condition of [Automatic approval](automatic-approval.md) holds. When GitHub refuses the inline comments, the review is posted with their text in its body instead. With inline notes on, the notes are dropped first (see [Inline notes](inline-notes.md)).
- **Asked first.** Before a review is computed, unless a recorded review is waiting to be published, the service asks GitHub which reviews of the app's own the pull request has, so a review it once posted is not paid for again. One on the live head that the database does not know ends the job as `already_reviewed`. One on another commit is recorded as posted when the database holds an unpublished review of that commit, and is otherwise logged as `unknown_review`.
- **Reviews after the first.** (A pull request against a gated branch, with the merge gate in `enforce` or `bypass`, is the exception: it is reviewed only when someone asks.) After its first review a pull request is reviewed again when its head moves (after the 180 quiet seconds; pushes inside them share one review), when its base moves, and on `/review`. A draft, an ignored author, a filtered base branch and the daily limit stop a review as they do the first. In dry run nothing is read from or written to threads, and none of what follows applies: every head is reviewed in full and its scores are given afresh. Out of dry run the review has one of three modes. The last review is the pull request's newest published review that is not a re-check. The first rule that applies decides:
  1. There is no last review, or its base branch is not the pull request's base branch now (or was not recorded, as in a run made before it was): a **full** review, as the first was.
  2. A `/review` on the head and base of the last review: a **re-check**.
  3. Otherwise the repository's `newHead` setting: `incremental` or `full`. When it is not written it is `incremental`, except on a gated pull request (the repository's gate is enabled, the pull request's base branch is in the gate's `branches`, and the mode is `enforce` or `bypass`), where it is `full`. In `shadow`, and on a pull request that is not gated, it is `incremental`. It can be set for all repositories and for one (see [Configuration](configuration.md)).
  - *What a full later review does.* It reads every file again, as the first review did, except a moved file that already has its score, and pays for it in full. A file whose diff a published review already read, with every block already scored, is sent last. The model is told which hunks are scored, so it is not asked for them again.
  - *What an incremental review and a re-check read.* They read the files with a thread that is due a verdict, and the files whose present diff no published review has read where they now stand: new files, files whose diff changed, and files moved or renamed with the same change. They do not read a file whose diff a published review has read and whose blocks are all scored, unless a thread of it is due. A file that only moved, once it has its score, is not read in any mode. For each file read, the request names the lines that changed since a published review last read it, and carries the last review's overview. That costs input tokens.
  - *The order.* In every mode the files with a thread due come first, then the files no published review has read as they are now, then the rest. A pull request too large for one review is therefore covered over several. A file that finds no room and that no earlier review covers is listed under `Coverage` as not reviewed, and counts as 100. A file that an earlier review covers and that finds no room keeps its scores and is not listed.
  - *What this costs.* A defect that the first review missed in code that has not changed since is not found by a later incremental review or re-check: the file is not read again, or, if it is read for other reasons, a major on a line that has not changed is listed and not posted (below). Set `newHead: full` to read everything at every head, and pay for it.
  - *Which lines count as unchanged.* "A line that has not changed" is measured for each file, from the last published review that read that file, by comparing the file's content then and now. When the content then cannot be read, or the file is new to the history, every line counts as changed. A finding the model raised on a changed line, and that was moved to a neighbouring line to be placed, counts as on changed code. A line that enters the diff without its own text changing counts as unchanged, as when the base branch moves under it.
  - *A finding on an unchanged line.* A blocker is posted as usual. A major is listed in the body, in the section `On code unchanged since the last review`, which follows `Findings`, and is not posted as a comment. A minor is dropped. A full review posts them all, and only counts the blockers and majors among them in the log.
  - *How the review opens.* An incremental review opens with `**Incremental review** of the changes since` and the first 12 characters of the last review's head; a `/review` adds `requested by @<login>`. A re-check opens with `**Re-check** requested by @<login>.` and says whether earlier threads were judged again, none was waiting, or none could be judged. A full review opens with a line only when it was asked for with `/review`.
  - *A push that tells nothing new.* When an incremental review started by a push or a change of base would read no file, owes no thread a verdict, and would show a person exactly what the newest published review shows (the same score for every file, the same parts to read, the same files not reviewed), no review is posted and the job ends as `nothing_new` (with automatic approval on, not when the newest published review was posted as an approval: see [Automatic approval](automatic-approval.md)). The run is recorded without a body, and it stores no scores for other pull requests: every score in it was kept from an earlier run. A `/review` is never ended this way: it gets a review, in the mode a push on that head would get. A head whose push ended this way has no review of its own: the older review stays the newest one, so the next push is measured against it, and a `/review` on that head is not a re-check.
  - *Already reviewed.* A head and base whose review is the pull request's newest published one are not reviewed again by a push (`already_reviewed`). A head that returns after another was reviewed (a force-push back, or a base changed and changed back) is reviewed again, in the mode above, against the newest review, not the older one it matches. It is posted, unless the review would show exactly what the newest one shows: then a push's job ends as `nothing_new`, as above.
- **Earlier threads.** Before a later review is computed, the service reads the pull request's review threads from GitHub through its GraphQL endpoint. A thread is the service's own when its first comment is a finding it posted and the database holds. A thread is judged when its finding is a major or a blocker and the thread is not settled: settled means resolved, and either a person replied or the app resolved it (GitHub names the app as the one that resolved it, and the app's own reply with its hidden line stands in the thread); with automatic approval on, the thread rule of approval must accept it too (see [Automatic approval](automatic-approval.md)). The model is shown each of the service's own threads that lies on a file it is shown: a judged thread with its replies (the last 30 only, each comment cut at 2,000 characters), the others without their replies. A thread is not shown on a file that moved without a change, nor when a file and its threads do not fit one call; in both cases it gets no verdict in that review. The threads' text is part of the call and is paid for: a judged thread can take about 22,000 tokens, and whoever may comment on the pull request writes that text. When a file and its threads do not fit one call, the file's test goes first, then its full contents, then its threads; when the threads go, the test and the full contents come back if they then fit. For each judged thread it may give one of three verdicts: `fixed`, `answered` or `open`. A verdict is kept only for a judged thread; `fixed` and `answered` need a reason; `answered` needs a reply in the thread by someone other than the app; and `fixed` is dropped when the review is of the head the thread was opened on.
  - *Written into the threads.* Once the review is published and its job is finished, a `fixed` or an `answered` verdict is written as a reply that opens with `Fixed.` or `Answered.` and ends with a hidden line that names the review and the commit. An `open` verdict is written as a reply opening with `Still open.`, and only when someone other than the app wrote last and the model gave a reason. When the app's own reply is last in the thread, a `fixed` or `answered` verdict rewrites it instead of adding another; an `open` verdict rewrites a confirmation to open with `Open again.`, and writes nothing after the app's own `Still open.` or when the thread has no reply. Nothing is written into a thread in which someone other than the app wrote after it was judged; it is judged again at the next review of a new head or base, or at a `/review`. Each write is made once, one second after the one before it; a write that fails is logged as `thread_write_failed` and not tried again, and changes nothing else. The threads are read again just before these writes; when that read fails, when recording the publication fails, or when the service stops after the review is posted and before the writes, none of them is made and nothing tries them again: the threads are judged again at the next review of a new head or base.
  - *Not posted again.* A blocker or a major finding that an earlier thread already raised is listed under `Already discussed`, with a link to the thread, and is not posted; a minor one is dropped without being listed. A finding was raised when an earlier thread on its file lies within 3 lines of it on the same side and is of the same class (blocker and major together, minor apart), or, for a thread whose line is no longer in the diff, when the thread quoted the same code. A minor thread never swallows a blocking finding, and a thread whose last verdict is `fixed` swallows nothing. When a thread was due a verdict, the `Overall` line counts the threads cleared, still open and not judged.
  - *A reply is judged later.* A reply someone writes in a thread is judged at the next review (of a new head or a new base, or a `/review`), not at once: nothing but a push, a change of base or a `/review` starts a review.
- **Resolving.** When the app has `contents` write, it resolves a thread whose verdict cleared it, after its reply landed. Without it the reply stands and the thread stays open, and the service logs `feature_off` with `resolving` at each start and raises an alert of that name. Without it a cleared thread stays open, so it is judged again at each later review and the app's reply is rewritten each time. The permissions are read once, at start: after changing them, restart the service. The service reads the permission the app asks for, not what an installation has accepted: until the owner accepts it, each resolve is refused and logged as `thread_write_failed` with `github_forbidden`.
- **`/review`.** A comment asks for a review when the first line of it that is not empty is `/review`, in any letter case, alone on the line or followed by a space and more text. Only an owner, a member or a collaborator of the repository is listened to. A command from anyone else is refused. When no run is recorded yet for the pull request's head (a review, or a failed try at one), the refusal gives that head its automatic job: the command may have stood in the way of a push's job. So such a comment can be what starts the review the head would have got at its next event. An accepted command gets an eyes reaction. A command the service refuses or whose review fails gets a confused reaction and one sentence with a short code: `not_allowed`, `closed` or `already_reviewed` when it is refused, `head_moved`, `review_failed`, `publish_rejected`, `render_failed` or `superseded` (another job for the pull request was waiting when this one was put back) when it failed. These ends are not answered: a command from someone without access that arrives while the pull request has a job waiting (it is not stored); a command that is replaced, while it waits, by a later `/review` from someone with access; one whose job was dropped because the pull request is gone (`not_found`) or no installation is known for it (`no_installation`); one whose job the service gave up on (it ran out of starts or grew too old); one whose job was cut by a restart, or met a database error before its review, while another job for the pull request was waiting; one whose pull request was closed while the review ran; and one the service could not record. An answer is written once: when GitHub refuses it, the log says `answer_failed` and it is not tried again. A command on the head and base of the last review is a re-check: the earlier threads are judged again, and files that no published review has read as they are now are read (see Reviews after the first for what that means, and what it does not read). A command on any other head gets the mode a push would give it, with the earlier threads. A command whose review ends because the head moved while it ran (`head_moved`), or ends without a published review (it failed, its text could not be rendered, or GitHub refused it) while the head the service has stored for the pull request is no longer the one it reviewed, starts over once: a new job for the new head takes its place, with the same requester and comment. It starts over only when the stored pull request was updated after the review started (GitHub's time of the update against the service's clock) and its head is not the one reviewed: a stored head that is merely behind, because the push's event has not arrived, starts nothing, and neither does a push whose event arrives only after the failure. The one that starts over says nothing to the requester: the new job's own end answers. A command that has started over does not start over again. This holds with no gate too, and costs one more review. A command is refused with `already_reviewed` only for a head on which GitHub lists a review of the app's own that the database does not know. It is never ended as `nothing_new`. A draft, an ignored author and the base-branch filter do not stop it. A bot's command is ignored. In dry run a command from someone with access is reviewed and recorded like any other job (in full, whatever the head; but a head and base that already have a recorded review end it as `already_reviewed`), and nothing is written on the pull request.
- **What the app needs.** Beyond what dry run needs, the app needs `pull_requests` write and `issues` write, and, to resolve threads, `contents` write (optional: without it the app still replies). The manifest of `npm run app:create` asks for all three. For the merge gate it also needs `checks` write and the event `check_run`, `statuses` read when `requiredChecks` are named and the organisation permission `members` read when a skip team is named (see [The merge gate](merge-gate.md)). For automatic approval it also needs `administration` read, to read whether the base branch's protection dismisses stale approvals (see [Automatic approval](automatic-approval.md)); the manifest asks for it. At start the service logs `feature_off` once for each thing a feature lacks and raises an alert of that name, and keeps running.
- **Mentions and HTML.** In text the model wrote, outside fenced code blocks, a zero-width space is put after the `@` of a mention, after a `<` that could start HTML (one before a letter, `/`, `!` or `?`), and after the `&` of a character reference, so none of them takes effect. This also holds inside inline code: copying such inline code copies the invisible character. Links are left as written, with these exceptions. In an address (text with `://` before it and no space between), an `@` that could start a mention is written `%40`; most sites read that as the same address. (An `@` right after a letter or digit, as in `user@example.test`, never starts a mention and is left alone; an address whose user part ends in another character stops working.) A link in angle brackets stays a link only when it starts with `http://` or `https://`, in lower case. A character reference inside an address still gets the invisible character, and so does an `@` in a link with no `://`, such as a relative path; such a link may stop working.
- **Tried once.** The first review, `/review`, a later review with its threads (reading them, replying, editing a reply and resolving), an incremental review, a re-check, a push that tells nothing new (a merge of the base branch, and a rebase), scores kept across reviews, and a score taken from another pull request were each tried once against a real GitHub App, on a small private repository, with each event sent to the service by hand. In that trial the model once sent a score for a block marked as already scored; the service ignored it, as it is built to. Inline notes were tried too: a note posted with a review, read back, not repeated at the next review, not answered, and not given again after a person resolved it; and one review with 56 inline comments, which GitHub answered with a server error after it had created it, and which the next start adopted without posting it again. A second scorer was tried too, on a small pull request: it scored the one block, a re-check asked nothing of either model, and after a push that moved the block's lines into another function it was asked for the block again. Not tried in that trial: the merge gate, which was tried later and in part (see [What was tried against GitHub, and what was not](merge-gate.md#what-was-tried-against-github-and-what-was-not)). Not tried: the command that creates the app, a review GitHub refuses for one comment, more than 50 flagged blocks in one review job, GitHub's own webhook deliveries and their redelivery, the `Already discussed` section and the fallback when GitHub refuses the inline comments, a finding on a line that has not changed, a thread judged in an incremental review, a hunk the model splits, a renamed new file, a block held to its stored score, the first review after an upgrade to surroundings, and anything at the size of a real pull request.

## Reading what a review would have posted

Every attempt at a review, finished or failed, is a row of `visto_ai.review_runs`:

```bash
docker compose exec db psql -U postgres -d visto -c "select id, owner, repo, number, outcome, cost, body from visto_ai.review_runs order by id desc limit 5"
```

`body` is the text that would have been posted (or was posted, out of dry run), `outcome` how the run ended and `cost` what the model calls cost, as recorded (see the daily limit below). The inline comments, and the notes when they are on, are in the `comments` column.
