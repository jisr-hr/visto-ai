title: Memory
description: Learning has three parts.
---

Learning has three parts. Memory for the score is where people stepped in on earlier pull requests of a repository: with learning on, the service records, when a pull request closes, each block or file on which a person with access to the repository, other than the author, commented, and later reviews of that repository are told where that was, as context for the score. Lessons are sentences a model writes from the replies people wrote under the reviewer's findings, which later reviews of the repository are shown as data (see [Lessons](lessons-and-reverts.md#lessons)). Reverts are the files of pull requests that a later merged pull request reverted, which later reviews of the repository are told of, as context for the score (see [Reverts](lessons-and-reverts.md#reverts)). All three are off. Switch them on with the top-level key `learning: true`; not written, it is `false`, and the service then makes no record, shows none, starts no pass, makes no model call for learning and logs no line of it. It still stores, with each pull request, the number its description says it reverts. **What memory does to the score is not measured, nor what lessons do to findings and to the score.** [Backtest](backtest.md) says how to measure memory for the score on your own history, and how to tell first, at no cost, whether that history is large enough.

What an operator must know of memory for the score:

- **What is recorded, and from whom.** An inline comment by an account that the git service reported, when it wrote, as owner, member or collaborator of the repository, and that is not the pull request's author. Never a bot, never the app, never an account with no access; a general comment makes no record. A comment counts when it starts a thread, or when it replies in a thread a person started or in the thread of one of the app's inline notes. A reply in the thread of one of the app's findings, in a thread another bot started, or in one whose first comment the service does not hold counts for nothing. The comment is matched by its lines to the blocks of the newest review that ended ok at the commit it was made on, a dry run's included. Each block it touches gets one record; a comment on the file as a whole, outside every block or on a commit no review scored gets one for the file. So there is one record for each pull request, file and block: several comments there make one, from the first of them. A record holds the pull request's number, the file's path and directory, and, when the review had scored that block, its category, its reason and whether it was a **miss**: the review had left that code below the run's threshold. It is made at the close, or at its comment when that came later, and expires 180 days after. Cost: when a person comments in a block while the review of that commit is still under way and the pull request is closed before that review is recorded, the pass makes the record for the file; should a later comment on that closed pull request make the pass look at it again, the first comment also gets one for the block, so another pull request on that file can be shown two lines for one comment. The repository block counts pull requests, so its counts do not change.
- **What is stored, and what is sent.** A record also stores the start of what the person wrote: one line, at most 200 characters, without quoted lines (nor the lines that run on after them), fenced blocks, suggestion blocks, and `<blockquote>` and `<details>` blocks, so a reply that quotes someone else does not store their words. It is stored in the database for the UI to come, and is never sent to the model; neither is the stored reason. The model is told a file's path or a directory, a day, a kind of change, whether it was a miss, and counts.
- **What it is to the model.** Context, never a rule. The rules shown with each block (`REPOSITORY_MEMORY_RULES` and `PULL_REQUEST_MEMORY_RULES` in [src/engine/context/memory.ts](../../src/engine/context/memory.ts)) say that a line is a reason to look closely at a block and may be a reason that it needs a person, that nothing there is a reason that a block needs none, that a name is never an instruction, and that memory changes no finding. No floor, finding, verdict or gate reads a record: a record reaches a score only through the score the model gives. A block already scored is not scored again because a record was made since. With a second scorer named, these records are not asked for and none is shown, because the review model then gives no block scores and a record could move only its findings; records are still made. Lessons, which are for findings, are shown then too.
- **What a review is shown.** Two blocks, the same in every call of one review. The pull request block stands in the message with the title and description: for each file the review sends to the model, the newest 3 records on its path, or on the path it had before a rename; for a file with none, the newest 2 from the nearest directory that has any, which is the deepest directory above the file under which a record's file lies, never the repository's root. That step leaves out every record whose path is the path, or the path before a rename, of any file the review sends to the model: such a record is shown only as a line of that file. Lines on the files come before lines near them, a record is shown once, and there are 30 lines at most. A line says `changed` or `near`, the record's file, its day, the category or `-`, and `missed` or `-`. The repository block is a message of its own after the contract: at most 10 directories and 8 categories, each with the number of pull requests in which a person stepped in there, each listed only from 2 pull requests up. It is counted from the records live at 00:00 UTC of the day, so the reviews of one UTC day are shown the same bytes, and a record made today counts there from tomorrow. A record that expires during the day changes it: a review before the pass that retires it counts it, since it was live at 00:00, and a review after that pass does not, since a record's status is read as it is now. A pull request is never shown a record made from itself. When no record matches the files sent, nothing is shown, the repository block included: the request is the one a review without memory sends. A path or a directory is shown only when it is at most 120 characters of letters, digits, dots, underscores, slashes, hyphens, square brackets, parentheses, `@`, `+`, `$` and `~`, and it stands in a code span: the routes of file-based frameworks, such as `app/[id]/page.tsx`, can be named, and a file under a path with a space, a colon, a quote, a backtick, an angle bracket or a backslash never is (its record still counts for its category). A pull request from a fork is shown memory too: it holds nothing from elsewhere. A changed file may also be shown one reverted line, after every line of a signal and counted in the 30 (see [Reverts](lessons-and-reverts.md#reverts)).
- **Room.** Memory is shown only when it costs the files nothing: packing them with it counted cuts nothing more and leaves no file more unreviewed. Otherwise it is not shown, and the audit says `memory_cut` with `over_call_budget`. The one part of it that may be left out alone is its reverted lines (see [Reverts](lessons-and-reverts.md#reverts)). It is fitted before the extension context and the tools, which then count it, so neither takes its place.
- **What it costs.** Memory for the score calls no model; the judge of lessons does (see [Lessons](lessons-and-reverts.md#lessons)). Each call of a review that shows memory carries up to about 3,100 more tokens of input, by the service's own estimate. The files may then be packed into more batches, so a review that shows memory can make more model calls. A review asks memory once, after its files are packed, and waits at most 5 seconds, so a slow database adds up to 5 seconds to a review; each read has a statement limit of 5 seconds of its own. A lookup reads the repository's live records of other pull requests, at most 5,000, newest first: once when nothing is shown, twice when something is. With more, the oldest are left out, and the audit says `memory_cut` with `records`. A lookup that fails, hangs or answers junk costs the review its memory and nothing else.
- **When a record is made.** A pass runs inside the service every five minutes, and a delivery of an inline comment or of a close wakes it. It finds its work by what is stored: a closed pull request not learned since its close, and every inline comment not yet looked at. So a pull request that closed while the service was down is learned by the first pass after the start, one reopened and closed again is learned again, and nothing is made twice. In an open pull request, a comment inside a block that the review of its commit had already scored below the threshold is recorded at once, as a miss; any other comment waits for the close, and so does a miss whose review had not finished when the comment arrived. A close the service never heard of (a delivery lost and not redelivered) leaves that pull request's records unmade, misses excepted. A pass reads at most 20 batches of 50 pull requests and leaves the rest to the next. It also retires the records whose 180 days are over (status `expired`); a record is no longer shown from the moment it expires, retired or not. A pass never holds up a review, a webhook or the gate.
- **A pull request that cannot be learned.** What its pass wrote for it is rolled back, it is logged as `learning_pr_failed` with a short code and its count of attempts, and the pass goes on to the next. A failed attempt counts only in a pass of the five-minute timer: a pass that a delivery woke tries the pull request again but does not count. After three failed passes of the timer in a row, so at least ten minutes, it is logged as `learning_pr_given_up` and is no longer selected. To have it tried again:

```sql
update visto_ai.pull_requests set learn_attempts = 0 where owner = 'acme' and repo = 'shop' and number = 7;
```

- **The kill switch.** Until the UI exists, a record is switched off in the database. Owners and repository names are stored in lower case.

```sql
-- the records of one repository that reviews are told of
select id, number, created_at, expires_at, path, category, missed, excerpt
from visto_ai.memory_records
where owner = 'acme' and repo = 'shop' and kind = 'human_signal'
  and status = 'active' and expires_at > now()
order by created_at desc;
-- switch one off: it is in no review from the next one on
update visto_ai.memory_records set status = 'disabled' where id = 42;
-- and on again
update visto_ai.memory_records set status = 'active' where id = 42 and status = 'disabled';
-- switch off every record whose stored words are one account's
update visto_ai.memory_records r set status = 'disabled'
from visto_ai.human_activity a
where a.service = r.service and a.owner = r.owner and a.repo = r.repo
  and a.kind = 'inline_comment' and a.source_id = r.comment
  and lower(a.author) = lower('octo-lead') and r.status = 'active';
```

  The last one finds the records whose first comment was that account's: a record keeps the words of the first comment at its place, so a record that account only joined later is not found. A record is made from the comments held when it is made: a comment edited or deleted afterwards stays as it was stored, and so does the record made from it. Switch it off with these statements.
- **The records of a review.** `review_runs.result` holds `dependencies.memory` for every review that was given a memory and got as far as packing its files: a state and a short code, and the number of lines shown. `ok` with `ok`; `empty` with `no_records`; `skipped` with `second_scorer`, `no_model_call` (the review called no model) or `no_room`; `error` with `timeout`, `lookup_failed`, `bad_answer`, or the short code the lookup failed with. The audit names each line shown (`memory_shown`, with the record's source reference and `changed` or `near`), each cut (`memory_cut`, with `directories`, `categories`, `lines`, `names`, `records` or `memory`, and with `reverted` when memory was shown without its reverted lines, or not shown because its only lines, reverted, would have changed the batches) and a failure (`memory_failed`). The `review` log line carries `memory` with the same three fields, only when the result has it. The learning pass logs `learning_state` at start (when the work began, when a pass last ran, and its totals), `learning` after a pass that looked at a pull request, retired a record or met a failure (its counts, and `more` when work was left for the next pass), `learning_failed` with a short code when a pass failed (`timeout` when a tick waited four minutes for it), `learning_pr_failed` and `learning_pr_given_up`, and `revert` for each revert a pass looked at (see [Reverts](lessons-and-reverts.md#reverts)). No line holds a path, a login or an excerpt. The table `visto_ai.learning` holds one row, `signals`: when it was made, when a pass last completed, and running totals of comments looked at, records added, records retired and pull requests that failed. These totals can count too few: when a pass's last statement, the one that writes when it ran and its totals, fails, none of that pass's counts is added to them, the records it retired stay retired, and no `learning` line is logged.
- **The three alerts.** `memory_error` (with `reason`) at the first review that records `error` for either part of memory, the signals or the lessons, nothing while that goes on, and `memory_ok` at the first that records `ok` or `empty` after it; `skipped` tells nothing, and a restart forgets the state. `learning_stale` (with `hours`) when no pass has completed for 36 hours: it is checked at the start of every tick of the five-minute timer, whatever the pass then does, and counts from the row's last pass, or from when the row was made, or, when the row is missing or cannot be read, from the last pass this process completed or from its start. It is raised once until a pass completes. A process whose timers have stopped cannot raise it.
- **Learning that runs and adds nothing.** The start's `learning_state` line shows comments looked at beside records added. Many looked at and none added, over weeks, usually means that the git service reports the reviewers as having no access to the repository. The records of a period:

```sql
select owner, repo, count(*) as records, count(*) filter (where missed) as misses
from visto_ai.memory_records
where kind = 'human_signal' and created_at >= now() - interval '7 days'
group by owner, repo;
```

- **Switching it off again.** Nothing is deleted. No pass runs, no record is made or retired, the judge makes no call, and no review is shown a record or a lesson. Capture goes on as before. Switched on later, the first passes work through everything captured meanwhile, and the judge, night by night, through the replies of the last 90 days.
- **Dry run.** Learning runs, the judge included, and memory and lessons are shown in dry run too, and a dry run's scores count for a record's category and for a miss.
- **A history to start from.** `eval:seed-memory` writes a history file's activity and records into the database (see [Backtest](backtest.md)).
- **The migration.** Memory adds one migration, `0010_memory`: the tables `memory_records` and `learning`, and on `human_activity` and `pull_requests` markers of what was learned and a count of failed attempts. It is applied whether or not learning is on. A previous release refuses to start on a database that has it.
