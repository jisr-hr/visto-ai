---
title: The UI
description: The service can serve a web UI at `/ui/`.
---

The service can serve a web UI at `/ui/`: sign-in by password, with accounts of the service's own, or through the GitHub App; two roles, admin and viewer; the layout of the approved screens (a sidebar with the screens the person's role may open, the mode, who is signed in and how, a light or dark theme and sign-out); Activity, which shows what runs now and the reviews of the last 30 days; the page of one review, where each of those reviews leads, which shows why it approved or did not, the score of each file, its findings, its usage, its approval record, its dependencies and the feedback on it; Settings, for admins, where the settings of the service are read and changed and the accounts are kept; and a page where a password account changes its password. It is off unless the config writes `ui.publicUrl`. **Sign-in through GitHub was not tried against GitHub:** in its tests and in its run under Docker, GitHub's authorize page, its code exchange and its reads of the user, of an installation and of a membership are stand-ins. Password sign-in, roles, Accounts and the accounts command were tried in the tests and in one run under Docker on a real Postgres; Settings in the tests only (see "What was tried" below). What follows is what its code does.

**Switching it on.**

- **The keys.** `ui.publicUrl`: the address people open the service at, an `https` address with no path, query or user name, or, for a try on one machine, `http://localhost` or `http://127.0.0.1`, with a port or none. `ui.accounts`: GitHub logins, at most 100, who may sign in through GitHub. `ui.team`: one team, written `<org>/<team-slug>`, whose active members may sign in through GitHub. For sign-in through GitHub, in the `app` block, `clientId`, the client id the app's settings page shows, and `clientSecret`, by reference (`{ env: APP_CLIENT_SECRET }` in [config.example.yml](../../config.example.yml) and [env.example](../../env.example)).
- **On or off.** The UI is on when `ui.publicUrl` is written. With `ui.publicUrl` alone, password sign-in is the only way in, and no client id or secret is needed. Sign-in through GitHub is on beside it when `ui.accounts` names a login or `ui.team` is written. With no `ui`, or a `ui` that writes none of the three keys, `/`, `/ui/` and `/api/` answer 404 `not_found`, as any unknown address does, and nothing is read for them. Cost: a config that wrote `ui.publicUrl` alone, which kept the UI off before this release, turns it on at the next start, and nobody can sign in until the accounts command makes an admin.
- **The refusal.** With `ui.accounts` or `ui.team` written, `ui.publicUrl`, `app.clientId` and `app.clientSecret` must be written. Each one missing is an issue of its own (`<key>: must be written when ui names accounts or a team`), and the start is refused, in dry run too, with no value quoted. The eval commands read the same file, so they refuse it too. A `clientSecret` that is written is read whatever `ui` says, and its variable must then be set; with sign-in through GitHub off, a client id or secret written is read and not used.
- **Who may sign in through GitHub is read from the file only.** Password accounts and every role live in the database (see "Accounts and roles" below).
- **The address.** Serve the service over HTTPS at `ui.publicUrl`: the session's cookie is `Secure`, and so is the cookie of a GitHub sign-in's state. `http://localhost` and `http://127.0.0.1` are accepted for a try on one machine; Chromium kept both cookies on `http://localhost` in a run under Docker, and `127.0.0.1` and other browsers were not tried. Open the service at `ui.publicUrl` itself: a password sign-in sent from a page at another name of the same service (`127.0.0.1` while `ui.publicUrl` says `localhost`, say) is refused as `origin`, and the state's cookie belongs to the host that set it, so a GitHub sign-in started at another name loses it on the way back, and is refused as `state`.

**On GitHub, before a real sign-in through GitHub can work.**

- On the app's settings page, set the **Callback URL** to `<ui.publicUrl>/api/auth/callback`, keep "Expire user authorization tokens" on, generate a **client secret** and put it in the variable `app.clientSecret` names, and copy the **Client ID** into `app.clientId` (see [Creating the app](create-the-github-app.md)).
- With `ui.team`, install the app on that organisation and accept the organisation permission Members read. While `ui.team` is written and the app lacks it, the service logs `feature_off` with the feature `ui` and `members:read` at each start, in dry run too, raises an alert of that name, and keeps running; a sign-in through the team is then refused.

**Building the files.** The image builds `ui/` in a stage of its own and keeps only the built files. To start the service outside Docker, build them first; the install reaches the network:

```bash
npm --prefix ui ci && npm --prefix ui run build
```

The service reads `ui/dist` once, at start, and serves it from memory, so restart it after a rebuild. With the UI on and nothing built, `/ui/` answers 404 while the API works, and the start logs `{ event: 'ui', files: 0 }`.

**Accounts and roles.**

- **Two kinds.** Each person who signs in is an account, a row of `visto_ai.ui_accounts`: a password account, with a name and a password of the service's own, or a GitHub account, whose name is its GitHub login. A password account's name is 1 to 39 characters, lower-case letters, digits, dots, underscores and hyphens, starting with a letter or a digit, and unique among password accounts; a GitHub account's is unique among GitHub accounts, letter case aside. A password account and a GitHub account may have the same name: Accounts marks a GitHub account with `GitHub`.
- **Two roles.** An account is an `admin` or a `viewer`. A viewer sees every screen but Settings: the sidebar lists no Settings entry, `/ui/settings` shows the not-found page, and the API answers a viewer 403 `forbidden` at every admin route (`GET /api/accounts` and the four `POST /api/accounts/...`), whatever the page shows. The role is read from the account's row at each request (see "Sessions" below).
- **The last admin** cannot be made a viewer or removed, from the UI or by the command (`last_admin`). An admin counts toward this unless it is a password account that has not chosen its own password yet, so an admin cannot step down in favour of one who has not signed in. A GitHub admin counts whatever the file says now. Cost: a GitHub admin whom the file no longer lets in while they are the only admin can no longer sign in, and only the command gets an admin back. So does turning sign-in through GitHub off (no account and no team left in `ui`) while a GitHub admin is the only admin: the command then gets one back with `make` or `reset`, since its `github` form is refused while sign-in through GitHub is off.
- **One change at a time.** Every role change, reset, removal, account made and GitHub row made runs in a transaction whose first statement locks the accounts table (`share row exclusive`, which leaves reads free). Under it the session of the admin who asked is read again, so an admin made a viewer or removed while their change waited changes nothing (`forbidden`, or `signed_out`), and two admins who make each other viewers at once leave one admin. Cost: a password sign-in's own writes (a wrong try, a right one) wait while a change holds the lock, for a few statements: a change draws and hashes its one-time password before it takes the lock.
- **A reset** (`Reset password` in Accounts, or the command's `reset`) gives a password account a new one-time password, clears its wait and ends all of its sessions. It keeps the role, so the last-admin rule does not refuse it. In the UI an admin cannot reset their own account (409 `own_account`; the row marked `You` has no `Reset password`), so no reset made in the UI can lock out the admin who made it; they change their password under `Change password`, ask another admin, or run the command. A GitHub account has no password and cannot be reset (409 `github_account`).
- **A removal** (`Remove`, confirmed in its row) deletes the account and its sessions at once. A removed GitHub account that the file still lets in comes back as a new viewer at its next sign-in.
- **At most 1,000 accounts**, of both kinds. Past them `New account` and the command's `make` are refused (`full`), and so is a GitHub login with no row of its own, at its sign-in and by the command's `github`.
- **The record.** Every change is a row of `visto_ai.ui_account_changes`: when; who made it (`by_kind` `password` or `github`, with the admin's name in `by_name`; `command`; or `sign_in`, for a GitHub row made at its first sign-in); the change (`made`, `role`, `reset`, `removed` or `password_changed`); the account it was made to, its kind and name as text, so the row outlives the account; and the new role, none for a removal. A first password chosen is recorded as `password_changed`, by the account itself. A role set to the one the account has already is no change, and is not recorded. Nothing in the record is secret. It has no screen yet: the second statement under "Who is signed in" below reads it.

**The first admin, and the way back in.** A new database has no account, and only the command `npm run accounts` makes the first admin. Run it where the service runs, with the service's config; under Docker, in the service's container:

```bash
docker compose exec app npm run accounts -- make --config /config/config.yml --name <name> --role admin
# with sign-in through GitHub only: the role of a login, before or after that person's first sign-in
docker compose exec app npm run accounts -- github --config /config/config.yml --login <login> --role admin
```

`make` prints a one-time password once: open `<ui.publicUrl>/ui/signin` within 72 hours, sign in with the name and it, and choose a password. The same command is the way back in when every admin's password is lost: `reset` an admin's account.

- **Its three forms**, each option once, in any order, and nothing else:
  - `make --config <path> --name <name> --role <admin|viewer>` makes a password account and prints `made <name> (<role>)`, `one-time password: <password>` and `expires at <time>`, an ISO time 72 hours on.
  - `reset --config <path> --name <name>` gives a password account a new one-time password, ends its sessions and its wait, and prints `reset <name>` and the same two lines.
  - `github --config <path> --login <login> --role <admin|viewer>` sets the role of a GitHub login, making its row when it has none, and prints `made the GitHub account <login> (<role>)`, `set the GitHub account <login> to <role>`, or `the GitHub account <login> is <role> already`, when nothing is written. While sign-in through GitHub is off in the config (no `ui`, or a `ui` that names no account and no team) it is refused before the database is opened: it prints `github sign-in is off` on stderr, since a GitHub account made then could never sign in, yet as an admin it would count toward the last admin.
  - The name given to `make` and `reset` is lower-cased, then held to the rule of a name before anything else is read: `reset --name Octo-Admin` resets `octo-admin`, and a name of another shape is a usage error.
- **Its exit codes.** 0 when done. 1 for a refusal, printed as its code alone (`bad_login`, `name_taken`, `full`, `not_found` or `last_admin`), for `not_migrated`, for a failure, printed as its short code, and for `github sign-in is off`. 2 for a usage error: the usage line (a name of another shape included), `usage: cannot read --config`, `config: <issue>` for each issue of the file, or `usage: accounts needs a database in the config`.
- **What it reads.** It reads the whole config with the service's own loader, so every variable the file names must be set, as for the service, and it uses only the database's address and whether sign-in through GitHub is on. It never migrates: on a database without the migration `0015_accounts` it prints `not_migrated` and writes nothing, so start this release once first.
- **What it writes.** Its changes keep the rules of the UI's, the last admin's included, and are recorded as made by `command`. It writes no log line. The one-time password is printed once, on its own line, and stored only as its hash. `npm run accounts` prints npm's own two lines first; a script that reads the command's lines runs `npm run --silent accounts -- ...`.

**Signing in with a password.**

- **The first step.** The sign-in page sends the name and the password to `POST /api/auth/password`. The name is trimmed and lower-cased before it is looked up, so a capital that a phone puts first does not matter; an account is made only with a name that already matches the rule. A right password makes a session (see "Sessions" below).
- **One-time passwords.** An account made or reset gets a one-time password: 20 characters drawn from `23456789abcdefghjkmnpqrstuvwxyz` (no `0`, `1`, `i`, `l` or `o`, no capital), each by Node's `randomInt`, about 99 bits. It is answered once, by the request that made it (or printed once by the command), stored only as its hash, and holds for 72 hours. A right one-time password makes no session: the page asks for a new password twice and sends it, with the name and the one-time password again, to `POST /api/auth/first-password`, which checks the one-time password again, sets the new password only over the hash it checked (a reset meanwhile wins: `refused`), and makes the session. An expired one-time password reads `This one-time password has expired. Ask an admin for a new one.`, but only once the right one-time password was given, so it tells nothing to someone who does not hold it. After `refused`, `expired` or `already_chosen` (the account chose its password already) the page forgets the one-time password and goes back to the first step, the name kept. Cost: until a password is chosen, the one-time password stays in the page's memory, and a first sign-in costs two verifies.
- **A password** is 12 to 128 characters, counted as code points and not normalized. Any characters may be in it, but a new password must be well formed (no lone surrogate) and hold no NUL, since with either two different passwords would hash alike, and it may not be the one-time password itself. A password typed at sign-in is checked whatever it holds. A password is stored only as an scrypt hash, N = 2^15, r = 8, p = 1, with a 16-byte random salt and a 32-byte key, written `scrypt$15$8$1$<salt>$<key>`, and compared in constant time. A stored value of another form, or one that names a higher cost, verifies nothing. Cost: each hash or verify holds one thread of Node's pool of 4 while it runs, with `maxmem` 64 MiB; measured on one machine at this cost, one took about 47 to 50 ms and about 33 MiB of memory, and four at once about 130 MiB at their peak; a password typed in another Unicode form does not match.
- **The wait.** After 5 wrong passwords in a row an account waits 15 minutes, by the service's clock: while it waits no password is checked against it, the right one included, and a check begun before the wait started signs in nothing. A right password, a reset and a change of one's own password clear the count and the wait. Cost: someone who knows a name can keep that account waiting (an admin's reset ends the wait), and a clock set back lengthens a wait.
- **One sentence for every refusal.** A wrong password, a name that does not exist, a name of another shape, a GitHub login typed as a name and an account that waits are all answered 401 `refused`, which the page says as `The name or the password is wrong. After five wrong tries in a row, an account waits 15 minutes.`, each after exactly one verify at the same cost: against the account's hash for a wrong password, and against a hash made at start for the rest. A wrong password also writes its count, which the others do not. That they last alike was not measured (see "What was tried" below). Should the hash made at start fail to be made (scrypt refused for memory, say), the next password sign-in or first password makes it again; a request that meets the failure answers 500 `internal_error` whatever the name, before any account is read, so a failure tells no name from another.
- **Another site's page.** `POST /api/auth/password` and `POST /api/auth/first-password` change something without a session, so each is taken only with an `Origin` header exactly `ui.publicUrl` (else 403 `origin`) and a `content-type` of `application/json` (else 415 `not_json`), checked before anything else is read: a page of another site cannot sign a browser in. Each body is a JSON object of exactly its keys (`name` and `password`; `name`, `oneTimePassword` and `password`), each a string, the name at most 200 characters and each password at most 1,024; anything else is 400 `bad_request`. A first password of another length is 400 `password_length`, and the one-time password itself 400 `same_password`. Every other route that reads a body needs JSON too. Cost: a script must send `Origin`, and behind a proxy that rewrites `Origin` password sign-in is refused; each such refusal is logged (see "The log" below).

**Signing in through GitHub.**

- **The start.** The sign-in page's `Sign in with GitHub`, shown only while `GET /api/auth/ways` answers that sign-in through GitHub is on, opens `GET /api/auth/start`. With it off, `GET /api/auth/start` and `GET /api/auth/callback` answer 404 `not_found` and read nothing. The start makes a random state and a random PKCE verifier, 32 bytes each, stores the SHA-256 of each for 10 minutes, and sets both in one cookie, `__Host-visto_oauth` (`Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax`). It then sends the browser to GitHub's authorize page with the client id, the callback, the state, the verifier's SHA-256 as the challenge (`S256`), and `allow_signup=false`.
- **The way back.** GitHub sends the browser to `GET /api/auth/callback`, which clears the state's cookie whatever it answers. It goes on only when the state in the address is the cookie's, is stored and has not expired, and the cookie's verifier is the one stored with it. A state is taken once. The code is then exchanged once, with the verifier and the client secret, for the person's token, which reads the account once (`GET /user`) and is dropped. The token is not revoked: it stays valid until GitHub expires it, after 8 hours by GitHub's documentation while "Expire user authorization tokens" is on. Each of sign-in's own calls to GitHub (the exchange, the read of the user, the read of an organisation's installation) ends after 10 seconds and is not tried again.
- **Who is let in.** A user account, never a bot or an account of another type, whose login is in `ui.accounts`, letter case aside: no further call is made. Otherwise, with `ui.team`, an active member of that team: the service reads the app's installation on the team's organisation with the app's own token, then the membership through that installation. The membership is read through the merge gate's client, which waits up to a minute for a call and tries once more; the sign-in waits for it 10 seconds at most and is then refused as `unverified` (reason `github_network`). A pending membership is not let in, and anything that cannot be read refuses the sign-in (`unverified`). By GitHub's documentation, a member of a child team of `ui.team` reads as an active member of it, so such a member may be let in; this was not tried. A person is their login: a login freed on GitHub and taken by someone else is let in under the name the file writes, with that login's account and role. A login with an underscore, as Enterprise Managed Users have, cannot sign in: the way back refuses GitHub's answer as `github`.
- **Its account.** A person let in finds their account by login, letter case aside, and the row takes the login as GitHub writes it now, and the time of this sign-in as its last. With none, the sign-in makes one, a viewer, recorded as made by `sign_in`; an admin may then change its role, and the row keeps it for every later sign-in. With 1,000 accounts and none of its own, the sign-in is refused as `full`, which the page says as `This deployment keeps 1,000 accounts at most. An admin can remove one.` A person refused lands on `/ui/signin`, which says why; one let in lands on `/ui/`.

**Sessions.**

- **The session.** A person signed in gets a session of 12 hours, the same whichever way they signed in. Its id, 32 random bytes, is the value of the cookie `__Host-visto_session` (`Path=/; Max-Age=43200; HttpOnly; Secure; SameSite=Strict`). The database keeps only its SHA-256, with the account it belongs to, the account's name at sign-in, the way it was let in (`password`, `account`, or the team as `ui.team` writes it), when it was made and last used, and when it expires. Neither cookie names a `Domain`, as the `__Host-` prefix needs. The state's cookie is `Lax` because a `Strict` cookie is not sent when GitHub sends the browser back. A password sign-in shows the page of the address it was made at, and `/ui/signin` leads to `/ui/`.
- **Read again at each request.** Each API request behind a session reads it from the database, with its account. It must not have expired. A password account's session holds while the account is one. A GitHub account's session holds while the way it was let in still holds in the running config: for `account` the login still listed, for a team the same team, letter case aside, whatever else the file names. So a restart with a login removed, or with the team changed, ends those sessions. The account's role, kind and name are read at each request: a role changed takes effect at the person's next request, with no new sign-in, and a removed account's sessions are gone with it. The membership is read only at sign-in: a member removed from the team keeps a session for up to 12 hours. The last use is written when the stored one is 60 seconds old or more. A database that fails while the session is read, or while its last use is written, is not a sign-out: the request answers 500 `internal_error` and logs `ui_failed`, and the page says `Not updating` (or, at its first read, that it could not reach the service) rather than showing the sign-in page.
- **A change of password, a reset, a removal.** Changing one's own password (`POST /api/me/password`, with the current password and the new one) ends the account's other sessions and keeps this one. A wrong current password counts toward the wait, and while the account waits the change is refused (400 `wrong_password`). A reset ends all of the account's sessions, and a removal deletes them with the account. A sign-in that was checking the old password when one of them was committed makes no session: it is refused.
- **Signing out** (the button beside the theme switch) is `POST /api/auth/signout` with the token for changes in the header `x-visto-csrf`. It deletes the row and clears the cookie. The token is the SHA-256 of `csrf:` and the session's id, stored nowhere, and given by `GET /api/me`; a request without it is refused (403 `csrf`). Cost: whoever holds a session's cookie can know its token. A session deleted in the database leaves its cookie in the browser until it expires, and it reads as signed out.

**The caps.**

- Expired sessions and states are deleted when a sign-in through GitHub starts, and at a password sign-in or a first password once its body holds, at most once a minute for each of the two, so a deployment without sign-in through GitHub deletes them too. While 1,000 states are live, `GET /api/auth/start` answers 503 `busy` and stores nothing, so a flood of starts can hold sign-in through GitHub off for up to 10 minutes.
- The UI's routes have places of their own, apart from the webhook's 20 and each module's 10, counted in three parts: 16 for the files (`/`, `/ui` and `/ui/...`, answered from memory with no database), 2 for the four sign-in routes (`/api/auth/start`, `/api/auth/callback`, `/api/auth/password` and `/api/auth/first-password`), and 4 for every other `/api` address, `/api/auth/ways` among them, so a flood of sign-ins does not keep the page from asking which ways are on. A request beyond its part's places is answered 503 `busy`, in plain text. So at most 6 of the UI's requests at once use the database, and they share its 5 connections with the reviews. Cost: two password sign-ins run at once at most, and a flood of them holds every sign-in off, as a flood of GitHub starts does.
- A body is at most 64 KiB (413 `payload_too_large`).
- Nothing limits requests by address or by minute: that belongs to the proxy in front. The wait after wrong passwords is an account's, not an address's.

**Who sees what.** Everyone signed in, admin or viewer, sees the same activity: every repository the service holds review jobs or runs of, the titles, numbers and short heads of their pull requests, and the login of whoever asked for a review with a `/review` or a `/done`, a commenter who may not command included; such a job is refused when it runs. The login of whoever asked for a re-run of the check is not shown. Nothing narrows this to a person's own access on GitHub: a member of the team without read access to a repository sees its titles, numbers and requesters. No answer but the two of the page of one review (below) holds the loaded config, a secret, a review's body, comments or result (only its counts of findings, its threshold and whether it found nothing new are read from it), GitHub's id of a review, a comment, an installation or a delivery, any author's login, or any text a person wrote but a title, with these exceptions for the accounts. `GET /api/me` holds the person's own name, kind and role. `GET /api/accounts`, an admin's only, holds every account's name, kind and role, whether it chose its password or waits, when it was made and by whom, and its last sign-in, never a hash, and an admin's change, but a removal, answers the account it changed in the same way. A one-time password is in the answer of the request that made it, and in no other.

**What the page of one review answers, and leaves out.** `GET /api/reviews/<run>` and `GET /api/pulls/<owner>/<name>/<number>/reviews` need a session and answer a viewer as an admin, for every repository the service reviews. They answer what Activity's answers do not: the model's own words (the text of each finding and each file's reason for its score, those below the threshold included), file paths, the pull request's author and its two branches, the login of whoever resolved a thread, a failed review's stage and code, the merge gate's mode, state and code, the last paragraph of an approval decision, the dismissal facts of each approval (withdrawn, dismissed on GitHub, a failed withdrawal's code and when it is tried again, whether it stood at a merge), and the feedback on the review: its counts and its newest 20 reasons, which are text a person wrote, at most 1,000 characters as stored. They never answer the config, a secret, a review's body but the paragraph, the comments as posted, the model's summary, the audit, a quote of code, the acceptance rows, the providers, the replies in a thread, the actor and the reason of a skip, the judge's verdicts, a memory record, a reason written for a block on another pull request, GitHub's id of a review, a comment, a thread, an installation or a delivery, or the base commit. Cost: part of this text was never on GitHub (the reason of every block and file below the threshold, which the posted review does not list, and every finding of a dry run), so a person the deployment lets in, with no read access to a repository on GitHub, reads text about its code that GitHub never showed anyone. **A login beside a feedback reason is the module's claim:** the service takes any login a module reports, so the page shows it only when it has GitHub's shape (letters, digits and single hyphens, no hyphen first or last, at most 39 characters), and does not verify it; a reason with any other login is shown with no name. A module's user can answer under someone else's login, and the page shows it as that login.

**The screens.** The sidebar's entries are Overview, Activity, Repositories, Memory and, for an admin only, Settings. Activity, the page of one review, Settings and Change password are the screens of this release. The Overview at `/ui/`, Repositories and Memory say "Coming in a later plan." Any other address under `/ui/` says "Not found", and so do `/ui/settings` for a viewer and `/ui/password` for a GitHub account. The sidebar also shows the mode (`Live` with the number of repositories the service has seen, or `Dry run`), who is signed in and how (`Signed in with a password`, with a link `Change password`, or `Signed in with GitHub`), a switch between a light and a dark theme (kept in the browser; with no choice it follows the system), and sign-out. A choice kept is applied by a small script of the page's own, `/ui/theme.js`, loaded in its head before anything paints, so the page never shows the other theme first.

- **In review now** lists the review jobs running or pending, at most 200, the running first. Each shows its pull request (the title linked to GitHub, or `<owner>/<name> #<number>` until a delivery has stored a title), its stage, who or what asked for it, when it started and a progress bar. Under them come the withdrawals of approvals waiting to try again after a failed try, at most 50, each with the code of that try and when it tries again; one that waits with no failed try (put back by a restart's recovery, say) is not listed. The header counts `<r> running, <q> queued`: running counts the jobs that run, are stopped or wait for pushes to settle, and queued the due ones and those waiting to try again; the sidebar's badge is the running count. Beside it stand the places of the review lane and of the withdrawal lane, and a queued job says when reviews are paused.
- **Recent reviews** lists the runs started in the last 30 days, newest first, 25 a page, with the total that match. Each shows its outcome, its highest score (red at or above the run's own threshold, 70 when it holds none; blue at 40 or above; green below), its findings by severity, its mode, cost, time taken and age. The outcome is the first that holds: `Failed`, `Nothing new`, `Drawn for the audit`, `Approved`, `Not posted` (out of dry run and not published), `Needs a person`, `Reviewed`; so a dry run never reads as approved. A failed run's score reads `None`, and a nothing-new one's `Kept`. The list is filtered by repository and by outcome (`Approved`; `Needs a person`, which takes the audit sample too; `Failed`), and searched by title (any part of it, letter case aside, with `%`, `_` and `\` taken as themselves) or by number, with or without `#`.
- **One review** (`/ui/reviews/<run>`, where each row of Recent reviews leads, for viewers and admins) reads everything it shows from what is stored; nothing is read from GitHub on a view. Under a link back to Activity it shows the pull request's title (`<owner>/<name> #<number>` when none is stored), its author, its two branches, the review's short head and, only for an `https` address, `Open on GitHub`. It is read once when it opens and again when the run changes, and the selector's list once for each pull request, so moving between the reviews of one pull request keeps the list; neither is polled. Cost: a page left open shows thread states, approvals and feedback as they were when it was opened, and a review made meanwhile joins the selector only when another pull request is opened or the page is loaded again. While it reads it shows only the link back and `Review <run>`; an answer 404, or an address whose run is not a whole number from 1 to 2147483647 with no leading zero (`/ui/reviews/007`, `/ui/reviews/2147483648`), says `Review not found`, the second without reading anything; any other failure says `The review could not be read.` with `Try again`.
  - **The selector** has one option for each review of the pull request, newest first, `Review <n> of <m>` with its age. `n` is the review's place among every run of the pull request by id, dry runs and failed ones included, and `m` their number. It lists the newest 200 and always holds this review, so a pull request reviewed more than 200 times lists its newest 200 and this one. Choosing one opens it. When the list cannot be read there is no selector.
  - **Why it approved or not.** The banner's decision is the first that holds: `Review failed`; `Not decided in dry run`; `Nothing new` (not posted, and the result says nothing new); `Not posted`; `Approved automatically`; `Not approved automatically` (the review carries an approval code); `No approval decided` (posted with neither: approval was off for the repository, or the review was already on GitHub when it was adopted). A dry run never reads as decided. The words of `Approved automatically` and `Not approved automatically` are the paragraph the posted review ended with, read from the last 4,000 characters of the stored body, only for a review whose approval code is set, and taken only when its last paragraph holds printable ASCII alone, is at most 2,000 characters and starts with the lead of its decision, so a body that merely ends alike is not read as one. A review with no such paragraph, posted before automatic approval existed or adopted, says a sentence of the page's own (`Posted as an approval.` or `Decided as <code>.`). Cost: the threshold, the thread rule and the detail of an unreadable check are stored nowhere else, so they cannot be written again from the code.
  - **The merge gate.** After the decision comes the gate's sentence: the newest gate evaluation of the pull request at the review's head, with its mode, its state and the number of blocking findings. A later review at the same head, a re-check, shares that evaluation, so the sentence is the gate's newest state for this commit, not its state when the review was posted. A state the page does not know is written as it was stored, in the code face.
  - **Scores by file** has one row for each scored file and one for each file not reviewed that has no score: first the reviewed files by score from the highest and, at a tie, by path, then the others by path, at most 500, the rest counted. The score that decides a file is its file level when that is above every block's own score or no block has one, otherwise its highest block (the first at a tie). The reason is that block's, except that a block scored on another pull request shows its category only, never the reason written there; the model's reason for the whole file when the file level's source is `whole_file`; and a sentence of the page's for every other source. The blocks are summarised, as the mockup draws them, not listed: `Whole file`, or their number and the lines of the highest (`2 blocks, the highest at lines 38 to 51`), with `kept from an earlier review` when the score came from one. A score a floor raised ends its reason with `<given>% was given; a block this file lost had scored <score>%.`. A file not reviewed says why in a sentence of the page's own for each stored reason (`no_diff`, `too_large`, `over_batch_limit`, `batch_failed` or `secret_file`), and the code in the code face for any other, and then what it counted as (` Counted as 100%.`). A reason is cut at 2,000 characters. Cost: a file's other blocks' scores and reasons are not on the page, which the posted review lists only at or above the threshold.
  - **Findings** are every finding of the stored result, of four kinds: placed on the diff, not on the diff, on code unchanged since the last review, and beyond the diff, sorted by severity, each kind in that order and each in its stored order at a tie. The header counts all of them by severity. At most 200 are shown, the rest counted, and a finding's text, cut at 4,000 characters, is shown as plain text with its line breaks, a span between two backticks on one line in the code face and nothing else of Markdown. Under them the page counts the earlier threads this review judged as the posted review's last line does (`n cleared, n still open`, and `n could not be judged`) and the findings it dropped as already discussed. Cost: the header's counts can differ from Activity's, which counts placed findings only.
  - **A thread's state** is derived from what is stored. A placed finding of a posted review is matched to a first comment of that review with the same path, side, severity and quote, in two passes over the comments in their stored order: each finding first takes the first unused comment with its own line, then each finding left takes the first unused comment whose line is null (GitHub's, stored as it answered). Its signals are a person's resolve or unresolve event on that comment's thread, timed when it was received, and each later posted review's verdict on it, timed when that review started. The newest decides, a person's event wins a tie, and with none the thread is open. The words are `Thread open`, `Resolved by <login>`, `Fixed in a later review` and `Answered in its thread`; a finding of a review that was not posted reads `Not posted`, one of a posted review with no first comment `No thread recorded` (its inline comment was refused or could not be read back), and a finding of another kind says where it is. Cost: a thread a person resolved that a later review still holds open reads open although GitHub shows it resolved; the app's own resolutions are not stored, so a thread the app resolved reads from the later review's verdict; a thread event that never arrived reads as if nothing happened; and the verdicts of every later posted review are read on each view of an early one, with no bound.
  - **This review** says who asked (`Automatic` or `By hand` when its job is gone, otherwise the words Activity uses), the mode with the files read, the outcome (`Published`, `Not posted`, `Dry run`, `Nothing new` or `Failed` with its code), how long it took and when it was posted. **Usage** shows the models that answered (at most 10), the calls, the input, cached and output tokens and the cost. A second scorer's usage is added into the review's, so Calls is the total, and a deployment with a second scorer cannot tell its calls here.
  - **The approval record** shows this review's own code, then the approvals the app posted on the pull request up to this review, newest first, at most 20, an approval after it appearing on its own page only. Each shows its review, its head and one of `Stands`, `Withdrawn`, `Dismissed on GitHub` or `Withdrawal failed`, and, when it stood at a merge, says so. A failed withdrawal's note starts `Dismissing it failed (<code>).`, the code `unknown` when the stored one is not a short code. A retry is said only when the pull request's withdraw job is waiting to try again after a failed try: `Tried again in <time>.` while that is half a second or more away, else `Trying again now.`; with no such job the note ends at `Dismissing it failed (<code>).`. That one job's time is shown on every approval whose withdrawal failed.
  - **Dependencies on this review** are as the review stored them: the review model, memory with the records shown, its lessons, and each MCP server and each extension (at most 50 of each), with the status (`Working`, `Nothing to add`, `Skipped` or `Failed`) and, when the status is not `Working`, its short code. A second scorer is stored nowhere apart and has no row, and dependency health over time is not on this page. A review that stored none says `None recorded.`
  - **Feedback** shows the helpful and not helpful counts and the newest 20 reasons, each in its own direction-isolated element, with the login beside it only when it has GitHub's shape (see "Who sees what"); with none it says `No feedback on this review.`
- **Reading.** The layout reads the activity every 5 seconds, and Activity reads the first page of the reviews every 15 seconds. Neither reads while the page is hidden, and both read at once when it shows again. A read that fails turns `Updating live` into `Not updating`; one answered 401 shows the sign-in page while the session that asked it is still the one signed in, so a late answer to the read of someone who has signed out since leaves whoever signed in after them as they are. Ages and times left are counted from the time each answer carries, not from the browser's clock. Cost: one person viewing makes about 16 requests a minute.
- **The sign-in page**, shown at any address while nobody is signed in, has a name, a password and `Sign in`, and `Sign in with GitHub` below them only while `GET /api/auth/ways` answers that sign-in through GitHub is on. A right one-time password turns it into `Choose your password`: the new password twice, then `Choose and sign in`, or `Cancel`, which goes back and forgets the one-time password. The two new passwords and their length are checked before anything is sent. A refusal keeps the name and empties the password fields.
- **Settings**, for admins only (a viewer is answered 403 `forbidden` by its routes and shown the not-found page), opens at its top. Its sections, each also a link in a row under the header, are General, Model, Repositories, Secrets, Access, Accounts, Changes and In config.yml. It reads the settings once when it opens and again after a save and after a save that found a change made meanwhile; it is not polled, and leaving the page drops what was typed, with no question.
  - **The header** says `Saved settings apply from the next review. A review already running keeps the settings it started with.`, counts the unsaved changes (`No unsaved changes` when there are none), and has `Discard` and `Save changes`. Discard is off while nothing is unsaved. Save is off while nothing is unsaved, while a save is out, and while a JSON field holds text that is not valid JSON (the field says `Not valid JSON.`, and that text counts as an unsaved change but writes nothing).
  - **General** holds dry run, learning, the daily spend limit, the reviews at once, the input tokens per call and the batches per review. **Model** holds the endpoint (read only text, `Set in config.yml`: the model's API key is sent to it, so only the file changes it), the model, the fallbacks, the two efforts (`Provider default`, `Low`, `Medium` or `High`, and `As written in config.yml` while the stored value is another fragment, which is kept until another is chosen), how the answer is asked for, the time limit, the three prices, the second scorer, its endpoint (read only text, `Set in config.yml`) and its time limit (both shown while it is on), the extra body and the extra headers (as JSON text). The second scorer is on while one of its two settings (its model, its time limit) is written; its key stays in the file, so switching it on from the page is refused with the key's issue, at the top of the page, unless the file writes `scorer.apiKey`.
  - **Repositories** lists `Defaults for all` and each repository that has an override, or that the service has stored a pull request of (at most 200 of those, besides the ones with an override), and the pane of the one chosen has the boxes Review, Score, Merge gate and Automatic approval. `Add a repository` takes an `owner/name`; one that overrides nothing is kept in the list until the page is left or reloaded and says `It is kept once it overrides a setting.`. In a repository's pane each setting says `From the defaults`, or, once written, `Overrides <the default's value>` with where it came from and `Use the default`, which takes the override back (the heading switches of the gate and of automatic approval do this too). The gate's rows show while the gate is on, and automatic approval's rows while it is. The `*` of `Reviewed on every push` means every branch (an empty list shows as a `*` that cannot be removed); the `Gated branches` row says that a `*` there is read as a branch of that name.
  - **Secrets** lists each secret the file writes by the name of the variable that holds it, `Set` or, for one the file could write but does not, `Not set`; a value is never shown. **Access** shows, read only, the address, the team and the accounts that may sign in through GitHub, which only the file sets. **Accounts** is the table and the account changes of the first release, below Access and as they were: the table of the accounts (the name, how it signs in, the role, the last sign-in, when it was made and by whom), `New account` (a name and a role, the name checked against the rule before it is sent), and in each row `Make viewer` or `Make admin`, `Reset password` (for a password account other than your own) and `Remove`, asked again in the row. After a make or a reset the one-time password is shown once, with `Copy` and `Done`. It is kept in the page's state only, and is gone after `Done`, a reload or leaving the page. The list is read again after each change, after a refusal `not_found`, and after a make refused as `name_taken` or whose answer was lost (none, a 5xx, or one that cannot be read), since its account may be there all the same; it is not polled.
  - **Where a value came from.** Each setting says `From config.yml at the start of <time>`, `Changed in the UI by <name>, <time>`, `The default` (a setting not written, for the globals and the defaults; for the defaults' way of reviewing a new commit, `Not set: incremental, and full where the merge gate holds pushes`), or, in a repository, the override line above. A setting taken back on the page and not yet saved says `Not written`; `Not set` is the word of the record (a value that was not written) and of a secret the file does not write.
  - **Saving.** Save sends only what differs from what the page read, with the version it read. The answer is the settings as they now are. If another save came first, the page says `Settings were saved meanwhile, here or in config.yml at a start. They were read again, and your changes are kept: save again.`, reads the settings again, and sends the same changes on top of the newer ones when saved again. A refusal shows each issue under its setting and all together at the top, each with where it is (General, Model, the defaults or the repository); an issue that names no setting (the audit key, the scorer's key) shows only at the top. What was typed while a save was out is kept. Two saves are checked whole: the settings saved with the file's other keys (what the next start would run on), and the settings in force until the restart with them (what runs now); the save is refused if either fails, and nothing is stored. A busy service says `The service is busy. Try again in a moment.`
  - **What waits for a restart.** A setting the service reads once when it starts carries the badge `Needs a restart` (dry run, learning, the reviews at once, the time limit and how the answer is asked for), and the second scorer's switch carries `On or off: needs a restart`. After one of them, or the second scorer's being on, is saved to another value than it started with, the row says `Takes effect when the service restarts` until a start reads it; the sidebar's mode (`Live` or `Dry run`) is the start's until then.
  - **Changes** is the record of every change, newest first, 50 a page with `Older`: when, who (`config.yml` or the account's name), where, the setting and its value before and after, each cut at 200 characters, `Not set` for a setting not written. A change made by the file is recorded at the start that read it. **In config.yml** is the saved settings as the file writes them, to copy, with `Copy`: replace those keys of the file with it to keep it in step; when the second scorer is off in the saved settings and the file still writes a `scorer` block, a third comment line says to remove that block. The service never writes the file.
  - **Cost.** A value written in plain text in an extra header or the extra body is shown on this page, stored in the three tables of `0016_settings`, recorded and exported; the schema takes no reference there, so put a key in `model.apiKey` or `scorer.apiKey`. The two endpoints are the file's alone, so no admin can send the keys to another address; one written with a credential in it (`https://user:token@...`, `...?key=...`) is shown to admins on this page, read only, and in the export, but is not stored in the settings tables or the record. Viewers never see Settings. Two admins saving at once: the second saves again. An unsaved page is lost to a reload.
- **Change password** (`/ui/password`, a password account's only) takes the current password and the new one twice. An empty current password is not sent, since the service would count it as a wrong try.
- **A role that changed.** An answer 403 `forbidden` to any request of the pages makes the page read who is signed in again, the page kept on screen, and applies the answer only while the same session is signed in. So an admin made a viewer keeps the Settings entry until their next request to an admin route, and loses it then; a viewer made an admin sees Settings once the page is loaded again.

**The stage of a running review.** Each review job writes its stage on its row, with the UI off too. What each reads as:

| Stage | When |
|---|---|
| `Waiting for pushes to settle` | A push's job (`synchronize`) in its 180 quiet seconds: pending, and due 180 seconds after it was made |
| `Waiting to try again` | Any other pending job not yet due, such as one put back after a failed try, or because the head moved while it ran |
| `Queued` | A pending job that is due |
| `Preparing` | Written first by the job; also a running job with no stage yet |
| `Reviewing`, batch n of m | Written before the first batch is sent, and as each batch ends |
| `Judging threads`, with the threads due | While a batch that holds a thread owed a verdict has not ended; such files are sent first |
| `Publishing` | Written just before the review is posted, so never in dry run |
| `Stopped` | A running job this service does not hold, left so by a job that could not record its run; it runs again at the next start |

A stage is written only on a running row, in order, and one that cannot be written changes nothing. A claim clears it, so a pending job's old stage is never read. After a crash the next start puts the running jobs back before it listens, so they read `Queued`. The progress bar is at 5% while preparing, at `10 + 80 * (n - 1) / m` percent at batch n of m, rounded, and at 95% while publishing: it moves only as batches end. A second scorer's step has no stage of its own: the last batch's stays shown. Cost: up to `m + 3` more statements for a review of m batches, with the UI off too.

**Headers and the cache.** Every answer of the UI's routes carries, exactly, `content-security-policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, `x-content-type-options: nosniff`, `referrer-policy: same-origin` and `x-frame-options: DENY`, the listener's own 503, 413 and 500 included. The fonts are bundled and no asset is inlined, so the page needs nothing from another origin. A file under `/ui/assets/`, whose name carries a hash, is cached for a year (`cache-control: public, max-age=31536000, immutable`); every other answer, `index.html` and every API answer included, is `no-store`.

**The routes.**

| Route | What it does |
|---|---|
| `GET /`, `GET /ui` | Sends the browser to `/ui/` (302) |
| `GET /ui/...` | A built file. An address that is no file gets `index.html`, so the application's own addresses reload; a missing file under `/ui/assets/` is 404. The path is never decoded, and never joined to a folder |
| `GET /api/auth/ways` | Whether sign-in through GitHub is on: `{ "github": true }` or `{ "github": false }` |
| `GET /api/auth/start` | Starts a sign-in through GitHub |
| `GET /api/auth/callback` | The way back from GitHub |
| `POST /api/auth/password` | A password sign-in, `{ "name", "password" }`: `{ "next": "signed_in" }` with the session's cookie, or, after a right one-time password, `{ "next": "choose_password" }` with none |
| `POST /api/auth/first-password` | The first password, `{ "name", "oneTimePassword", "password" }`: `{ "next": "signed_in" }` with the session's cookie |
| `POST /api/auth/signout` | Signs out, with the token for changes |
| `GET /api/me` | The account's name, kind (`password` or `github`) and role, the token for changes, `live` or `dry_run`, and the repositories the service has stored a pull request of (in lower case, sorted, at most 200) |
| `POST /api/me/password` | Changes one's own password, `{ "current", "password" }`, with the token: 204 |
| `GET /api/activity` | What In review now shows |
| `GET /api/reviews?repo=&outcome=&q=&before=` | A page of Recent reviews: `repo` an `owner/name`; `outcome` `approved`, `needs_person` or `failed`; `q` the search, at most 100 characters; `before` the run to page from. A parameter written empty reads as absent, and a malformed one is 400 `bad_request` |
| `GET /api/reviews/<run>` | One review's page; 404 `not_found` when no run has that id |
| `GET /api/pulls/<owner>/<name>/<number>/reviews` | The reviews of a pull request, newest first, at most 200, with their place and the total |
| `GET /api/accounts` | An admin's: every account, at most 1,000, and the time of the answer |
| `POST /api/accounts/new` | An admin's, with the token: makes a password account, `{ "name", "role" }`; 201 with the account, its one-time password and when it expires |
| `POST /api/accounts/role` | An admin's, with the token: `{ "id", "role" }`; 200 with the account |
| `POST /api/accounts/reset` | An admin's, with the token: `{ "id" }`; 200 with the account, a new one-time password and when it expires |
| `POST /api/accounts/remove` | An admin's, with the token: `{ "id" }`; 204 |
| `GET /api/settings` | An admin's: `now`, `version` (the id of the newest change, 0 with none), `global`, `defaults` and `repositories` (each setting as `written`, `value`, `source` (`by`, `name`, `at`, or null), `restart` and `waits`), `scorer` (`on`, `waits`), `endpoints` (`model` and `scorer`: the two endpoints as the file writes them, read only; `scorer` is read from the file, so it shows while the scorer is off too, with the default address when the block writes none, and is null only when the file has no scorer block), `secrets` (`kind`, `of`, `variable`, never a value) and `access` |
| `PUT /api/settings` | An admin's, with the token: `{ "version", "changes": [{ "scope", "path", "value" }] }`, 1 to 500 changes, none twice; a scope is `global`, `defaults` or a repository as `owner/name` in lower case; a change with no `value` takes the setting back to its default; 200 with the settings as they now are, 409 `changed` when another save came first, 422 `invalid` with `issues` (`scope`, `path`, `message`) |
| `GET /api/settings/changes?before=` | An admin's: `changes` (`id`, `at`, `by`, `name`, `scope`, `path`, `before`, `after`), 50 at most, newest first, and `next`, the id to pass as `before`, or null; a `before` that is not a whole number up to 2147483647 is 400 `bad_request` |
| `GET /api/settings/export` | An admin's: `{ "text" }`, the saved settings as `config.yml` text |

The files are served to anyone: they hold no data. Every `/api` route but `/api/auth/ways` and the four of sign-in needs a session, and without one answers 401 `signed_out`. A method other than a route's own is 405, with `allow` (`GET, PUT` for `/api/settings`), and any other `/api` address is 404 `not_found`. The two routes of one review need a session, viewers included, and count against the API's 4 places. A path under `/api/reviews/` or `/api/pulls/` that is not exactly one of them, whatever the method and with or without a session, is 404 `not_found` and reads nothing: a run that is not a whole number from 1 to 2147483647 with no leading zero, an owner or a name that, lower-cased, is not 1 to 100 letters, digits, `_`, `.` or `-`, a number of another form, a trailing slash, or an escaped letter. Another method on a path that fits is 405 with `allow: GET`. A run no row has is 404 `not_found`, and a pull request with no run answers an empty list; owner and name are lower-cased before they are looked up. Behind a session the checks run in this order, and none reads anything after it refuses: the session (401 `signed_out`), the token for a change (403 `csrf`), the admin role (403 `forbidden`), then a body's `content-type` of `application/json` (415 `not_json`) holding a JSON object (400 `bad_request`). A body that is not of the route's exact keys is 400 `bad_request` too. An account is named in the body by its id, a whole number from 1 to 2147483647; a role is `admin` or `viewer`; a name is a string of at most 200 characters. The settings' own refusals: a body that is not exactly `version` and `changes`, a version that is not a whole number from 0 to 2147483647, a setting that is none of the editable ones, one named twice, and a value holding U+0000 or a lone surrogate are 400 `bad_request`, with nothing stored. The account routes' own refusals: 400 `bad_name`; 401 `signed_out` and 403 `forbidden`, the admin's session read again under the lock; 404 `not_found`; 409 `name_taken`, `full`, `last_admin`, `github_account` and `own_account`. Changing one's own password refuses a GitHub session (409 `github_account`), a new password of another length (400 `password_length`), and a wrong current password or an account that waits (400 `wrong_password`). The reads answer JSON, and so does each refusal at an `/api` address (400, 401, 403, 404, 405, 409, 415, 500), as `{ "error": "<code>" }`. The two routes of sign-in through GitHub answer with a redirect, but for a start refused as `busy`, which is JSON, and for both while sign-in through GitHub is off (404); the two of password sign-in answer JSON. Sign-out, `POST /api/me/password` and `POST /api/accounts/remove` answer 204 with no body. The files' 404 and 405, and the listener's own 503 `busy` and 413, are plain text.

**The log.** One `ui_signin` line for each way back from GitHub, with `way` (`github`), `outcome` and `reason`. The outcomes: `ok`; `denied`, when the person refused on GitHub's page; `state`; `github`, when GitHub could not be reached, refused the code, or answered what the service does not take; `not_allowed`; `unverified`; `full`, when 1,000 accounts are there and none is the login's; `failed`, when a database step failed. The reason is a short code, such as `oauth_refused`, `github_502` or `not_installed`, or null. One `ui_signin` line, with `way` `password`, for each request to `POST /api/auth/password` and `POST /api/auth/first-password` that the route answers; a request the listener refuses as busy or too large writes none. Its outcomes: `ok`; `choose`, a right one-time password; `refused`; `expired`; `already_chosen`; `bad_request`, with the code it was answered as its reason (`origin`, `not_json`, `bad_request`, `password_length` or `same_password`), so a proxy that rewrites `Origin` shows as `origin`; `failed`, with a short code. Every other password outcome has no reason, so a password typed into the name field is never logged. One `ui_account` line for each change to an account made through the service, a GitHub row made at a sign-in included, with `change` (`made`, `role`, `reset`, `removed` or `password_changed`) and the new `role`, null for a removal; the command logs nothing. One `ui_failed` line, with the route's name (`me`, `activity`, `reviews`, `signout`, `ways`, `own_password`, `accounts`, `account_new`, `account_role`, `account_reset`, `account_remove`, `review`, `pull_reviews`, `settings`, `settings_save`, `settings_changes` or `settings_export`) and a short code, when a request fails. One `ui` line at start, with `files`. One `settings` line at each start, with `from_file`, the number of settings the file changed at this start, and `from_ui`, the number of settings whose value came from the UI. One `settings_save` line for each save that reached the work, with `outcome` (`saved`, `changed` or `invalid`) and `changes` (the values changed when saved, the changes asked otherwise); a save that fails on the database is logged as `ui_failed` with `settings_save`. No line holds a login, a name, a password, a one-time password, a hash, a code, a state, a verifier, a token, a cookie, a session id or the client secret: who signed in, and who changed what, is read from the database.

**Who is signed in, and who changed what.** In the database (`docker compose exec db psql -U postgres -d visto`):

```sql
-- who is signed in now, and as whom
select a.kind, a.name, a.role, s.via, s.created_at, s.last_used_at, s.expires_at
from visto_ai.ui_sessions s join visto_ai.ui_accounts a on a.id = s.account_id where s.expires_at > now() order by s.last_used_at desc;
-- the record of account changes, newest first
select at, by_kind, by_name, change, account_kind, account_name, role from visto_ai.ui_account_changes order by at desc, id desc limit 100;
-- sign everyone out
delete from visto_ai.ui_sessions;
```

`last_used_at` is written at most once a minute. A session whose row is gone reads as signed out at its next request.

**The settings, and who changed them.** In the same database:

```sql
-- the settings in the database, and where each came from
select scope, path, value, set_by, set_by_name, set_at from visto_ai.settings order by scope, path;
-- the latest changes
select at, by, by_name, scope, path, old_value, new_value from visto_ai.setting_changes order by id desc limit 50;
```

`settings_file` holds the file's editable part as of the last start, which the next start compares the file with. A setting not in `settings` reads as its default.

**With the UI off,** the service still stores each pull request's title from its deliveries, each review job's stage, and a withdrawal's retry code, and still runs the sync of the settings at each start, which then copies the file's editable part whole: it runs on the file's settings, and what the UI saved before is gone, each change recorded as made by `config.yml`, so the settings put back when the UI is switched on again are the file's; nothing of the accounts is read, and nothing is answered, logged or posted that was not. A title, which its author wrote, is stored and shown to everyone signed in, escaped. A pull request stored before the UI's first release shows `<owner>/<name> #<number>` until its next delivery.

**The migrations.** The UI adds three. `0014_ui`: the title on `pull_requests`, the stage's five columns and the retry code on `jobs`, and the tables `ui_sessions` and `ui_states`; every row stored before it reads as no title, no stage and no code. `0015_accounts`: the tables `ui_accounts` and `ui_account_changes`, and on `ui_sessions` the account each session belongs to. `0015_accounts` deletes every session first, so everyone signs in again once. `0016_settings`: the tables `settings` (the database's part of the editable settings, with where each came from), `settings_file` (the file's part at the last start) and `setting_changes` (the record); it copies nothing itself, the first start after it does. Each is applied whether or not the UI is on. A previous release finds a migration it does not know and refuses to start on that database (`unknown_migration_applied`), so it cannot be put back. The page of one review adds none: everything it shows is stored already, and its two routes only read.
