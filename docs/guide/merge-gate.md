---
title: The merge gate
description: The merge gate is a check that the service writes on a pull request's head commit.
---

The merge gate is a check that the service writes on a pull request's head commit. A repository that makes it a required check in GitHub cannot merge a gated pull request while a finding of the app that is a major or a blocker is neither judged by the review of the current head nor answered by a person in a resolved thread. It is off unless a repository switches it on. **The gate was tried against a real GitHub App only in part, and never as a required check, so how it holds a merge has not been seen.** What follows is what its code does, as its tests show it with GitHub stood in by a fake; [What was tried against GitHub, and what was not](#what-was-tried-against-github-and-what-was-not) lists what was seen and what has still to be.

**Setting it up.**

- **The gate block.** Under `repositories.defaults.gate`, and for one repository under `repositories.overrides.<owner/name>.gate`, where each key written replaces the default's. The keys, with what they are when not written: `enabled` (`false`); `branches` (no list: it must be written when the gate is enabled, and a config that enables the gate with none is refused at start); `checkName` (`AI Review`; 1 to 100 printable ASCII characters); `mode` (`enforce`; or `shadow` or `bypass`); `clearByReply` (`true`); `skipTeam` (nobody; written as `<org>/<team-slug>`); `requiredChecks` (none). [config.example.yml](../../config.example.yml) shows them. The block is the deployment's: it is set in the config file or, once the service has started, by an admin in the UI's Settings, under Repositories (see [Configuration](configuration.md)); nothing in a reviewed repository, `.visto-ai.yml` included, can set it. A save in Settings with the gate on and no branch is refused at `Gated branches`. A change saved there applies at each pull request's next event; the start's sweep of checks, the bypass alert and the app's permission check (`feature_off`) read the setting at the next start. A `*` in `branches` is read as a branch of that name, which gates nothing, unlike the review filter `baseBranches`, where `*` means every branch.
- **Make the check required in GitHub.** Add a ruleset, or a branch protection, on the gated branches that requires the check by its name and by this app. Nothing in the service does this, and until it is done the check is written and holds no merge. Gating a pull request and requiring the check are two settings, in two places.
- **An app made by `npm run app:create` has the permissions.** An **existing app** is given these by hand, in its settings: `Checks` read and write; `Commit statuses` read, only when `requiredChecks` are named; the organisation permission `Members` read, only when a skip team is named; and the event `Check run`. Each installation must then accept them. The service reads the app's permissions once, at start, so **restart it afterwards**. For what is still missing it logs `feature_off` with the feature `gate` at each start, and raises an alert of that name (the missing item is `checks:write`, `event:check_run`, `statuses:read` or `members:read`), and it keeps running. Like the permission to resolve threads, it reads what the app asks for and not what an installation has accepted, so it cannot see a permission that was not accepted: a write that GitHub then refuses fails as described under "When it fails".
- **Roll it out in `shadow` first.** Reviews then run as without a gate and the check is written, so the checks can be watched before anything relies on them.

**What the `check_run` subscription costs.** An app subscribed to `check_run` may be sent the `created` and `completed` events of every check run of its repositories, whether or not a gate is switched on. Each one is stored as an ignored delivery in the `deliveries` table, which is never pruned. After a downtime the service reads at most 10 pages of GitHub's delivery log (see [Leaving dry run](leave-dry-run.md)), so that traffic can push real missed events out of its reach. The only `check_run` event the service acts on is a re-run of its own check. **How many such deliveries arrive was not measured: do not switch a gate on in a busy repository before the number of these deliveries has been seen on a quiet one.**

**Which pull requests are gated.** A pull request is gated when its repository has the gate enabled and its base branch is in `branches`, compared exactly, letter case included. The review filter `baseBranches` has no say in this. What changes for a gated pull request depends on `mode`:

- In `enforce` and `bypass` it gets no review when it is opened, reopened, made ready for review, pushed to or given a new base branch (the job is dropped as `gated`). It is reviewed when someone with access comments `/done` or `/review`, or re-runs the check. A review at a new head is `full` unless `newHead` is written (see [Reviews after the first](leave-dry-run.md)). A draft, one by an ignored author and one against a branch outside `baseBranches` get the check too, and need `/done` like any other.
- In `shadow` it is reviewed exactly as without a gate, and it gets the check.
- A pull request of the same repository against a branch that is not in `branches` is reviewed on a push as before.
- Each open gated pull request is given its check at its next event (an opening, a reopening, a push, a retarget, a thread event, a reply, a command, the end of a review job), and, for every pull request the service has stored as open, at each start of the service (see "What else it costs" below for the cost). A pull request the service has no stored row for gets its check at its next event or command, and at start once the gate has written its check.

**The check.** It is a check run named `checkName`, written on the pull request's head commit, so a new commit has a new check, which waits for `/done` again. Its link goes to the pull request's page. Its states:

| Title | Status and conclusion | When |
|---|---|---|
| `Waiting for /done` | queued | No review of this head exists yet, and none is under way |
| `Reviewing` | in progress | A review of the pull request that will run is running in the service or waiting for its turn. A stranger's waiting `/review`, which is about to be refused, and a push's job on a pull request that is reviewed only when asked, which is about to be dropped as `gated`, do not count |
| `Review waiting: reviews are paused (spend_limit)` or `(model_error)` | queued | A review is waiting and reviews are paused. For `model_error` the text says only that reviews are paused on the reviewer's side |
| `No blocking findings`, `1 finding, none blocking` or `N findings, none blocking` | completed, `success` | The head has its review and nothing blocks. `; N files not reviewed` follows the title when the review left files unread |
| `1 blocking finding is open`, `N blocking findings are open` or `Blocking findings open: N (M listed in the review only)` | completed, `action_required` | The rule below finds a finding that blocks |
| `Review failed (<code>): comment /done to retry` | completed, `failure` | The newest review of this head failed or was not published |
| `Could not evaluate (<code>): comment /done to retry` | completed, `failure` | The review was published, and the threads could not be read to decide |
| `Skipped by @<login>` | completed, `success` | The skip team skipped this commit |
| `Gate bypassed` | completed, `success` | The repository is in `bypass` |
| `Earlier approval not withdrawn (<code>)` | completed, `failure` | An approval of the app's own that the service could not dismiss still stands, whatever a skip or a review says (see [Automatic approval](automatic-approval.md)) |
| `Withdrawing an earlier approval` | in progress | An approval of the app's own of another head or base branch still stands and is being dismissed, whatever a skip or a review says |

GitHub does not reopen a completed check run: an update that asks for `queued` or `in_progress` is answered and changes neither its status nor its conclusion. So when a completed check must wait or review again (a `/review` or a `/done` on a head whose check is decided, or leaving `bypass`), the service writes a new run of the same name on the commit. GitHub then lists, and the pull request counts, only the newest run of that name; the older one stays on the commit. An update from `queued` or `in_progress` to any state, and from one conclusion to another, is made in place.

**The rule.** After a review, the check is `success` in three cases only: the head has its review and no thread blocks and no review of this head left a blocking finding without a thread; a skip is stored for this head; the mode is `bypass`. The head's review is the newest published review whose head and merge base are the live ones: a re-check counts, and after a retarget the pull request is not reviewed. A read that fails never reads as "nothing blocks".

- **Which threads block.** A thread of the app's own whose first comment is stored as a finding of severity major or blocker, and that is not cleared. Minors, notes and findings that no thread holds never block.
- **The three ways a thread clears.** (1) The review of the current head kept a `fixed` or `answered` verdict for it, and no one but the app has written in the thread since. (2) The app resolved it, and the newest verdict that any published review kept for it is `fixed` or `answered`. (3) With `clearByReply` on: it is resolved and a person (not the app and not a bot) has replied in it.
- **A thread resolved with a click and no reply does not clear.** The check's summary names it, and the next review judges it again.
- **A reply is not read, and its author's access is not checked.** "Will fix" counts, and so does a reply written before the last push. On a public repository the author of a fork's pull request can therefore turn the check green alone, by replying and resolving, while the merge itself still takes write access. A person's comment in a thread after the review judged it ends that verification.
- **The app's own thread with no stored finding blocks,** as a finding of unknown severity: the stored findings are first completed from the threads, as a review does, and what is left unknown no review can judge. It clears by a person's reply and a resolve, or, with `clearByReply` off, by a skip. A minor or a note whose record was lost blocks in the same way, and so does a thread that another deployment of the same app left.
- **What does not block, and is counted.** A major or blocker finding the review could not place on the diff, and a major raised on code unchanged since the last review in an incremental review. The review lists them, and the summary counts them.
- **A review whose inline comments GitHub refused blocks** while it holds a major or blocker finding placed on the diff. Those findings are in the review's text and in no thread, so no reply can clear them: the commit stays blocked until a new commit is reviewed, or the skip team skips it. The rule looks at the newest published review of this head and base that was posted without its inline comments, so a `/done` on the same head, which publishes a re-check with no findings, does not turn the check green. If that review's stored result cannot be read, it blocks too. With `newHead: incremental` the review of the next commit reads only what changed, so it may not raise those findings again.
- **Files not reviewed** are counted in the title and do not fail the check. A team that wants a person to look at them requires an approving review in GitHub: the service never approves a pull request with a file not reviewed (see [Automatic approval](automatic-approval.md)), so where a repository requires one, a gated pull request with a green check and such a file still waits for it.
- **Verification is read from the database.** A database that lost a run loses its verifications, and those threads block until the next review.
- The summary lists at most 50 threads, each with its file, its line and a link to the thread, and says how many more there are. A path is shown in printable ASCII, with every other character and the backtick shown as `?`. The finding's own text is not shown.

**With `clearByReply: false`,** only a review clears a thread (or the app's own resolve after one does), and a resolved thread with a person's reply is judged again at the next review. Three kinds of thread no review can judge then clear only by a skip: one whose file left the pull request's diff, one whose file was not sent to the model, and the app's own thread with no stored finding. The check's summary says which, on the thread's line.

**Evaluated again without a review.** On a resolve, an unresolve and a reply in a review thread, by anyone (the app included), the check is looked at again about three seconds later; each new one restarts the wait. An edit and a deletion of a comment are not taken in, so a deleted reply changes the check only at its next evaluation. It is also looked at after a review job leaves, when reviews are paused or resume or change their reason, and at each start for every stored open gated pull request. Each look reads the pull request and the check from GitHub (and the review threads, when the head has its review), and writes only when the check would change.

**`/done`, `/ai-review-skip <reason>` and a re-run.**

- **The words.** A command is read from the first line of a comment that is not empty, in any letter case: `/done` alone or followed by a space and more text; `/ai-review-skip` followed by a space and a reason, which is the rest of that line.
- **Where they are commands.** `/done` and `/ai-review-skip` are commands only in a repository whose gate is enabled; elsewhere they are ordinary comments. On a pull request of such a repository that is not gated, `/done` is a `/review`, and the skip is refused as `not_gated`.
- **Who may.** `/done` and the skip: an owner, a member or a collaborator of the repository, as for `/review`; the skip also needs the commenter to be an active member of `skipTeam`, whose organisation must be the repository's owner (a pending membership is none). A re-run: GitHub decides who is offered the button, and the service does not check it, so a re-run made through the API by a bot is honoured too. A re-run names the pull request in the check's `external_id`, or else the first one GitHub lists for the commit, so a fork's re-run works. A re-run of another app's check or of another name is not taken in, nor is a re-run of a whole check suite.
- **What a `/done` does.** It gets an eyes reaction. If the rule, evaluated now, says the head is already green (passed, skipped or bypassed), nothing is started and files not yet reviewed are not read either. When `requiredChecks` are named and every one is green on the head (a commit status or the newest check run of that name saying `success`; `neutral` and `skipped` are not green), it also gets one sentence saying so. Otherwise a review is queued. A `/done` or a re-run that finds a review of the pull request that will run, running in the service or waiting for its turn, joins it: no second review. Only a review that will run is joined: one asked for by a re-run or by someone who may command, or an automatic one on a pull request that is not reviewed only when asked (`shadow`, or a branch outside the gate's list). A stranger's `/review` that waits is about to be refused, and a push's job on a pull request reviewed only when asked is about to be dropped as `gated`: neither is joined, and the `/done` stores its own review. A review asked for by `/done` or a re-run starts over once when the head moved while it ran, and also when it ends without a published review (it failed, its text could not be rendered, or GitHub refused it) while the stored pull request was updated after it started and its head is no longer the one it reviewed (the review that starts over says nothing; the new one's end answers). A `/done` or a re-run does not join a running review that has started over, since that one does not start over again and the command would be lost: it stores its own review, while a waiting one is still joined. That costs one more review.
- **The answers.** A `/done` that is refused gets a confused reaction and one sentence with a code: `not_allowed` or `closed`. One that fails after its starts are used up gets a sentence that says it could not be handled. A skip is accepted with an eyes reaction, and refused with a confused reaction and a sentence with one of `not_allowed`, `closed`, `not_gated`, `stale_head`, `missing_reason`, `no_skip_team`, `not_team_member` or `membership_unverified`. A failed membership lookup is `membership_unverified`, never "not a member": nothing is skipped. A re-run is never answered in a comment. A command replaced by a later one while it waits is not answered.
- **What a skip does.** It holds for one commit: the head the service knew when the comment arrived. It is refused as `stale_head` when a commit has been pushed since, so a skip typed while a push is in flight has to be typed again. A review does not undo it: a `/review` or a re-run on a skipped head runs and posts, and the check stays skipped. Only a new commit ends it. The check says who skipped and why: the reason is shown as one line, at most 300 characters, in a code span, with control characters and characters that change the direction of text removed and each backtick written as an apostrophe. The login, the reason and the comment are stored in `gate_overrides`. The skip team's name is written nowhere on GitHub: the texts say "the team that may skip". A misspelt team name is not noticed at start: it reads as "not a member" for everyone.
- **A re-run** on a pull request that is no longer gated does nothing and says nothing. One on a commit that is no longer the head asks for no review and says nothing, and so does one under `bypass`.

**Modes.**

- **`shadow`:** reviews as before, the check written. A push that tells nothing new leaves "Waiting for /done", as it would under the gate before a `/done`.
- **`bypass`:** every check is written green (`Gate bypassed`) at its next evaluation, and a gated pull request is reviewed only when asked. The service logs `gate_bypass` and raises the alert of that name at each start in which a repository is in `bypass`. Leaving `bypass` takes effect at the next start, for the pull requests the service has stored: at start, every stored open gated pull request is asked for (see "What else it costs"), so the checks written green are decided again.

**When it fails.** A failed evaluation is written at once as `failure` (`Review failed`, `Could not evaluate`), with a short code, and tried again twice, after 10 and 60 seconds; the check says that the service tries again only while it does. A job that gives up, and one that the runner gives up as too old or out of starts, raises the alert `gate_check_failed` with its code, once for each code in a run of the service, and asks for nothing more. Alerts go to the log always, and to `alerts.webhook` when you wrote it. **A read or a write of GitHub that fails leaves the check GitHub already shows, and that can be a green one that no longer holds**: a thread unresolved while the check cannot be written, or a review asked for on a green head. Fail closed bounds what the service writes, not what GitHub keeps. During an outage of the checks API, or once a job has given up, a merge can pass on a stale check; the alert is the only sign, and the next event or start tries again. Every stored open gated pull request is asked for at each start, so a check the service gave up on is tried again then. A pull request whose check can never be written (the app was removed from the repository) is tried three times at each start, with one alert for each code.

Every call to GitHub has a time limit of 60 seconds, and one that runs out is read as `github_network`. That limit holds for the reviews too: a slow answer that would have come after a minute is now a failure, tried again by the rules that exist.

**In dry run** no gate job is stored and no check is read or written. A gated pull request still gets no review on a push, `/done` is a `/review` recorded like any other dry review, and a skip and a re-run do nothing.

**What else it costs, and where it ends.**

- The check follows an event by the time a gate job takes to start, and, for a thread event or a reply, by about three more seconds. The app's own replies cause one evaluation that changes nothing.
- **Two pull requests of one repository with the same head commit share one check. This is a known hole, and nothing in the service guards against it.** GitHub attaches a check run to a commit, not to a pull request. Each pull request is evaluated on its own (its review, its threads, its skip), and the one evaluated last decides what the commit's check says, so one of the two can show a green check on the strength of the other's review, or of a skip given for the other. It happens when one commit is the head of two pull requests of one repository, for example opened against two branches, whether both are gated or only one is (the check is then the gated one's, and the other pull request shows it too).
- **At each start the service asks for the check of every stored open pull request that is gated,** whatever its last recorded state, one that was closed or gone included: a pull request closed, then reopened and changed while the service was in dry run, would otherwise keep a green check. That is one evaluation for each open gated pull request at each start: reads of GitHub (the pull request, the check and, when the head has its review, its threads). A check that needs no change is read and not written.
- While reviews are paused, the check of each pull request with a review waiting is brought up to date each time the pause begins, ends or changes its reason: one evaluation for each such pull request each time.
- Whether the gate is in use is decided when the service starts (out of dry run, with some repository's gate enabled). A gate switched on in the UI holds each pull request from its next event, but until the next start the sweep of checks and this asking for the checks of waiting reviews are not made, and the bypass alert and the app's permission check wait too. Every check of the model's key, at the start and at each upkeep, sends the start's headers and endpoint, so a wrong header saved in the UI can leave reviews paused (`model_error`) until the next start, and reviews can fail while the check passes.
- An objection written into a thread that the app resolved holds nothing while the thread stays resolved: the app resolved it after a review cleared it, and a person's reply after that is not read. Whoever objects unresolves the thread; it then blocks until a review judges it again.
- A pull request that stops being gated (its gate switched off, or its base moved out of `branches`) keeps the check it had, and nothing writes it again: "Waiting for /done" can stand on a pull request nobody has to answer.
- A pull request the service has no stored row for, one opened before the app was installed, is asked for at start too, once the gate has written its check, in a repository whose gate is enabled, with the installation of its newest job that has one; one whose newest evaluation says it is closed or gone is left alone, since nothing else would stop the sweep from reading it at every start (a reopening stores a row). Jobs are deleted after 14 days, after which such a pull request has no installation to be asked with and waits for its next event or command (a thread event, a reply, a `/review`, a `/done`, a re-run or the end of a review job), because the job carries the installation the event brought. Until then GitHub shows its own wait for the required check.
- A pull request the database still holds as open though it was closed costs one read of GitHub at each start. With hundreds of open gated pull requests at a start, a command typed right after it waits behind the sweep's evaluations.
- Gate jobs have their own places (see [Running it](running-the-service.md)), so a check is written while a review runs.
- The gate adds one migration, `0008_gate`, which is applied once: a previous release finds a migration it does not know and refuses to start on that database.

## What was tried against GitHub, and what was not

**Tried once,** with a real GitHub App on a small private repository, a real review model and a real second scorer. The app has no webhook, so each event was built from what GitHub's API answers and sent to the service by hand.

- The names GitHub gives the permissions (`checks`, `statuses`, `members`) are the ones the service looks for.
- The app created its check run on a head commit and found it again by name and app.
- A whole round: a gated pull request opened got `Waiting for /done` and no review; `/done` got the eyes reaction, `Reviewing`, a review, and a blocked check that names the threads; a person's reply and a resolve cleared one finding within seconds, with no review; a resolve with no reply cleared nothing, and the summary said so; a reply in that thread turned the check green; `/done` on the green head started no review; an unresolve turned it red again; a push gave the new commit its own waiting check and left the old commit's alone; a re-run, sent as an event built from the real check run, started a review that ended green; and `/ai-review-skip` with no team named was refused with its sentence.
- At start the service wrote the check of a gated pull request it had stored from before.
- A completed check run cannot be reopened by an update, and a new run of the same name replaces it (see above). As first built the service tried the update; it noticed that GitHub had kept the old status, tried again, and the check was right once the review ended. It now writes a new run, and that was tried too: a `/review` on a head whose check had passed got a new run that said a review was under way and was then completed, and GitHub listed and counted that run alone.

**Not tried:** the check as a required one, so not how each state holds a merge; how `action_required` reads on the pull request's page and whether a re-run is offered there; GitHub's own deliveries (which `check_run` deliveries the app is sent and how many, a thread event for a resolve made in the page, what a real re-run carries, for a fork too); a skip by a member of the team, a skip typed after a push, and every answer to a team membership question; the required CI checks of `/done`; `shadow`, and `bypass` across two starts; a review GitHub refuses inline; a pause of reviews; the manifest flow with the new permissions; and how a path with odd characters and a skip's reason read in the summary.
