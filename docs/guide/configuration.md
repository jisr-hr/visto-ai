---
title: Configuration
description: config.example.yml documents every key.
---

[config.example.yml](../../config.example.yml) documents every key. Copy it to `config.local.yml`, which git ignores. A secret is never written in the file; the file names the environment variable that holds it.

The top-level `extensions` block names extension modules, each with a name, a path or package and its options, in which a secret is named by reference as `{ env: VARIABLE }` (see [Extensions](extension-modules.md)).

The top-level key `learning` switches memory on for every repository of the deployment, or off for all: memory for the score, lessons and reverts. It is `false` when not written, and is no key of a repository (see [Memory](memory.md)). The number a description says a pull request reverts is stored either way.

The top-level key `auditKey` names, by reference, the secret the audit sample of automatic approval is drawn with: at least 32 characters, needed while a repository has `autoApprove` true with an `auditShare` above 0, and read, so needed in the environment, whenever it is written (see "The audit key" under [Automatic approval](automatic-approval.md)).

The top-level `mcpServers` block names MCP servers, each with a name, an address, headers (a secret by reference) and the tools the model may be offered (see [MCP tools](mcp-tools.md)).

`model.toolChoice` says how the model is made to answer through `submit_review`. With `forced`, what you get when the key is not written, every request names the tool, as before. Use it unless your endpoint refuses a request that names a tool for your model: every review then fails at the model stage with a provider error. On 2026-11-23 the first endpoint the project supports refused such requests for some newer models, before they reached the model, and accepted `auto`. Then set `toolChoice: auto`: every request leaves the choice to the model, the tools of a request stay what they are, a turn that must end the call says so in a line, and an answer there that does not call `submit_review` is invalid output and takes the one retry. What `auto` costs: the model may answer in prose, which costs one more request, and two such answers in one model call fail that part of the review. With MCP servers named, a model that calls one of their tools again on the closing turn and again on its retry fails that batch the same way (see [MCP tools](mcp-tools.md)). The key changes the requests with no MCP server too, and the eval commands honour it.

The merge gate has its own block, `gate`, under `repositories.defaults` and `repositories.overrides` (see [The merge gate](merge-gate.md)). One repository setting decides how a later head is reviewed: `repositories.defaults.newHead`, which `repositories.overrides` can set for one repository. `incremental` (what you get when it is not written, except on a gated pull request in `enforce` or `bypass`, where not written means `full`) reads only what changed since the last review; `full` reads the whole pull request at every head, and costs what a first review costs. It changes nothing for a first review, for a head on a different base branch (always full), or for a `/review` on the head and base of the last review (always a re-check). See [Reviews after the first](leave-dry-run.md).

**What the UI edits, and what stays in the file.** Once the service has started, the editable part of the config lives in its database too, and an admin changes it in the UI's Settings (see [The UI](the-ui.md)). The editable part is `dryRun`, `learning`, `limits` (its four keys), `model.baseUrl`, `model.model`, `model.fallbacks`, `model.effort`, `model.toolChoice`, `model.timeoutSeconds`, `model.prices`, `model.extraBody` and `model.extraHeaders`, `scorer.baseUrl`, `scorer.model` and `scorer.timeoutSeconds`, and, under `repositories.defaults` and each of `repositories.overrides`, `primaryBranches`, `ignoredAuthors`, `baseBranches`, `newHead`, the `score` keys (`threshold`, `inlineNotes`, `autoApprove`, `approvalThreads`, `auditShare`) and the `gate` keys (`enabled`, `branches`, `checkName`, `mode`, `clearByReply`, `skipTeam`, `requiredChecks`). A list or a map is one setting. What stays in the file, shown read only on the screen, is what the service needs before it reaches the database or what holds a secret by reference: `app`, `database`, `server`, `alerts`, `auditKey`, `extensions`, `mcpServers`, `ui`, `model.apiKey` and `scorer.apiKey`. The second scorer is on while one of its three keys is in the database; its key stays in the file, so switching it on in the UI needs the file to write `scorer.apiKey`. An override key that names no repository (not `<owner>/<name>`, lower case) is not copied into the database; it never had an effect. A reviewed repository's own `.visto-ai.yml` still only adds protection: these settings are the deployment's.

**Keeping the file and the database in step.** At each start, after the migrations and before anything reads a setting, in one transaction, the service compares each editable setting in the file with what the file said at the previous start, which it keeps in the database. A setting changed in the file (written, edited or removed) goes into the database and replaces what the UI saved, recorded as made by `config.yml`; a setting removed from the file goes back to its default. A setting not changed in the file keeps the database's value, so a change made in the UI survives a restart. The first start copies every setting the file writes. A file that fails alone stops the start as before, and nothing is copied. A file that passes alone but does not pass with the settings saved in the UI put back stops the start too, and copies nothing: each issue is printed as a `config:` line, then, when some setting came from the UI, the sentence `Saved in the UI: <the file paths of those settings, at most 10, then "and <n> more">; with them config.yml does not pass.` and how to settle it, then `start_failed`, and the process exits with 1. Changing those settings in the file, to another value or removing them, settles it, since a setting changed in the file wins at the next start. Cost: the service and its UI stay down until the file is fixed, and the sentence names every setting saved in the UI, not only those that clash; the issues say which clash. While the UI is off (the file writes no `ui.publicUrl`), each start copies the file's editable part whole, every difference recorded as made by `config.yml`: the service runs on the file's settings, and what the UI saved before is gone from the database (the record keeps it, and the export taken before gives its text).

**When a saved setting applies.** A saved setting applies at the next review or event, with no restart: every repository setting (each event, gate job, withdrawal job and review job reads the settings in force), the limits read for each review (`limits.inputTokensPerCall`, `limits.batchesPerReview`), the daily spend limit (read at each look; a limit raised above what is spent alerts again when the spend reaches 80% or the limit again), the model's `model`, `fallbacks`, `effort`, `extraBody`, `extraHeaders` and `prices`, and the scorer's `model` and `timeoutSeconds`. A review already running keeps the settings it started with. These are read once, when the service starts, so a change saved to them waits for the next start, which the screen says: `dryRun`, `learning`, `limits.queueConcurrency`, `model.baseUrl`, `model.timeoutSeconds`, `model.toolChoice`, `scorer.baseUrl`, and whether the second scorer is on. Three costs follow. A merge gate switched on in the UI holds each pull request from its next event, but the start's sweep of checks, the bypass alert and the app's permission check for the gate wait for the next start. Automatic approval switched on in the UI is checked for the app's Administration read at the next start only. And the start's check of the model's key sends the headers and the endpoint of the start, while reviews send the saved headers.

**`*` in the base filter.** `baseBranches` holding `*`, or an empty list, reviews every branch, and `*` beside names reads as every branch too (git refuses `*` in a branch name, so no branch is shadowed). The gate's `branches` are different: a `*` there is read as a branch of that name, which gates nothing; the Settings screen says so beside them.

**The export, and the evals.** The UI never writes `config.yml`. Settings gives the saved settings as text to copy back: the `dryRun`, `learning`, `limits`, `model`, `scorer` and `repositories` keys as the saved settings make them (the settings written, and the references the file writes inside `model` and `scorer`), as YAML, after two comment lines. It reads back as the same settings. Replacing those keys of the file with it keeps the file in step; the file's comments in those blocks are lost when it is replaced. The eval commands (`npm run eval:replay`, `eval:backtest`, `eval:judge` and the other `eval:*` scripts) read `config.yml` only, so an eval run after a change in the UI uses the file's settings until the export is copied in.

**What the screen, the record and the export show.** No secret's value is in the database's settings, the screen, the record or the export. But `model.extraBody` and `model.extraHeaders` take no reference, and `model.baseUrl` and `scorer.baseUrl` take any `http` or `https` address, so whatever the file writes in them (a header's value, a user and password or a token in an address) is shown to admins on the Settings screen, stored in `settings`, `settings_file` and `setting_changes`, recorded and exported. Nothing is refused. Keep a key in `model.apiKey` or `scorer.apiKey`, by reference. To read the settings and the record by hand, see "The settings, and who changed them" in [The UI](the-ui.md).
