---
title: How a review runs
description: The engine is one function, `review(input, deps)`.
---

The engine is one function, `review(input, deps)`. It reads a pull request and returns a structured review. It writes nowhere: not to GitHub, not to a database. That is what lets the evaluation call it directly.

1. **Read.** The pull request, its changed files and their contents come through a read-only source. The GitHub source only ever sends `GET` requests.
2. **Build context.** The model gets the diff with an anchor on every line (`R142    |+code`), the full contents of changed files where they fit, and the test file that belongs to a changed file. When the config names extension modules, it also gets what they supply, such as a ticket's text and its acceptance criteria (see [Extensions](extension-modules.md)). A large pull request is split into batches, up to a limit; what does not fit is reported as not reviewed, unless an earlier review already covers that file. A secret file is never sent to the model: it is listed as not reviewed (`secret_file`) and scores 100%, so a person looks at it. A file is secret by its name alone: `.env` and `.env.*` other than `.env.example`, `.env.sample` and `.env.template`; anything under a `.ssh` directory; and files named exactly `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519`, `.netrc`, `_netrc`, `.npmrc`, `.pypirc` or `.dockercfg`. Other files that may hold credentials, such as `*.pem`, `*.key` or `.aws/credentials`, are sent like any file.
3. **Mark untrusted text.** Everything that comes from the pull request, what an extension module supplies, and what an MCP tool returns, is wrapped in data markers with a random token, the same in every call of one review. The contract tells the model that text inside the markers is data, never instructions. With memory switched on, the model is also shown where people stepped in on earlier pull requests of the repository (see [Memory](memory.md)). That holds no words a person wrote, only names of files and directories, days, kinds of change and counts that the service computed, so it is not wrapped; each name stands in a code span. Lessons are words a model wrote from a person's reply, so, like everything a person's words led to, each is wrapped in the data markers, under rules of its own (see [Lessons](lessons-and-reverts.md#lessons)).
4. **Ask the model.** The model must answer through one tool call, `submit_review`, so the answer is structured data and not prose. Every request names that tool, unless `model.toolChoice` is `auto` (see [Configuration](configuration.md)). When the config names MCP servers, the model may first call their tools, a bounded number of times (see [MCP tools](mcp-tools.md)). The rules it follows are in [contract/review-contract.md](../../contract/review-contract.md).
5. **Check the answer.** An answer that names no changed file is sent back once, and then rejected. A finding on a file that is not in the pull request is dropped. A finding on a line that can take a comment stays there. One on a line that cannot is placed by the code it quotes: on the nearest line of the file whose text is the quote, on its own side first, unless the full file shows the quote on the very line it named (then it is about code outside the diff). Otherwise it is moved to the nearest line that can take a comment, within three lines. One its own file cannot take goes to another file of the same batch when exactly one line there has the quote as its text; anything else is listed separately. A finding on a test, documentation, generated, vendored or lock file is dropped: such a file is still read and scored, and its section tells the model that no finding is asked there.
6. **Render.** The service builds the review text from the structured result. The layout, the severity tags and the lists are the service's. The model supplies the overview, the text of each finding, and a score for each changed block, which the service checks before it counts: a score that is not a whole number from 0 to 100 leaves its block counted as 100.
