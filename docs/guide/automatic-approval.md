---
title: Automatic approval
description: With automatic approval on for a repository, the service posts a review as an approval when, at the moment it posts it, every condition below holds.
---

With automatic approval on for a repository, the service posts a review as an approval when, at the moment it posts it, every condition below holds. Otherwise it posts the review as a comment, as it does with approval off, and the review's last paragraph says which condition did not hold. It is off unless a repository switches it on. With it on, a share of the pull requests it would approve, 5% unless the config says otherwise, is drawn for the audit sample and posted as a comment for a person to review (see "The audit sample (condition 6)" below). What follows is what its code does.

**Setting it up.**

- **The keys.** Three keys of the `score` block: under `repositories.defaults.score` for every repository, and under `repositories.overrides.<owner/name>.score` for one, where each key written replaces the default's. With what they are when not written: `autoApprove` (`false`); `approvalThreads` (`strict`, or `gate`: see "Which threads hold it back" below); `auditShare` (of the pull requests the service would approve, the percentage sent to a person anyway as the audit sample, a number from 0 to 100 that may hold a fraction; 5; 0 switches the sample off). [config.example.yml](../../config.example.yml) shows them. They are read only from the deployment config: nothing in a reviewed repository, `.visto-ai.yml` included, can set them. With `autoApprove` true and an `auditShare` above 0, the config must also write the top-level `auditKey` (below).
- **The audit key.** The draw is keyed with a secret of the deployment's, named by reference at the top level of the config, as `auditKey: { env: AUDIT_KEY }` (the variable's name is yours to choose), and kept like the webhook secret. Its value must hold at least 32 characters, for example the output of `openssl rand -hex 32`, and is used as it is, spaces included. While `autoApprove` is `true` with an `auditShare` above 0 (the default 5 included) for the defaults, or for a repository once its override is merged with them, a config that writes no `auditKey` is refused at start: the service prints `config: auditKey: must be written while autoApprove is true with an auditShare above 0`, once however many repositories need it, and exits with 2. A key written is read whatever the repositories say, so it must be set: a variable not set, or set empty, prints `config: auditKey: environment variable <NAME> is not set`, and a value of fewer than 32 characters `config: auditKey: environment variable <NAME> must hold at least 32 characters`; each exits with 2, and none quotes the value. All three hold in dry run too, where nothing is drawn. The eval commands that read the config (`eval:replay`, `eval:backtest`, `eval:judge` and `eval:seed-memory`) read the key the same way and stop on the same issues, though they draw nothing: with the deployment's config, run them with the variable set to any value of at least 32 characters, never the deployment's real key. The placeholder in [env.example](../../env.example), `change-me-audit-key`, is shorter than 32 characters on purpose: the service refuses it, so it is never used as a key. When neither the defaults nor any override, merged with them, has approval on with a share above 0, no key is needed.
- **The base branch's rule.** The service approves only where the base branch's own rules dismiss an approval when new commits are pushed: a ruleset that applies to the base branch, or its branch protection, that requires a pull request and dismisses stale approvals. In GitHub's settings both call it "Dismiss stale pull request approvals when new commits are pushed", under "Require a pull request before merging"; the two reads below find it as `dismiss_stale_reviews_on_push` and `dismiss_stale_reviews`.
- **Require an approving review there too.** Nothing in the service reads whether the base branch requires an approving review, nor whether it requires a code owner's: the reads below look only at the dismissal of stale approvals, and nothing says so when no approving review is required.
- **The permission.** The branch protection is read with `administration` read. Out of dry run, when any repository has approval on, the service checks at start that the app has `administration` read, `pull_requests` write and the event `pull_request_review`; for each one missing it logs `feature_off` with the feature `approval` (the missing item is `administration:read`, `pull_requests:write` or `event:pull_request_review`), raises the alert of that name, and keeps running. An app made by `npm run app:create` has the permission, also with approval off. An **existing app** is given `Administration` read by hand in its settings; each installation must accept it, and the service is restarted, since it reads the app's permissions once, at start. It reads what the app asks for, not what an installation has accepted: a protection read GitHub then refuses gives `rule_unreadable` (below), unless a ruleset says the rule is on.

**The conditions, in the order they are read.** They are read after the review is computed and recorded, just before it is posted, with the repository's settings as they read then. In parentheses, the number of each condition in section 6.4 of the design; its condition 1 is the switch itself.

1. The pull request is open, and still at the head and merge base the review was computed for (condition 5). Otherwise nothing is posted, as with approval off: the job ends `closed` or `head_moved`.
2. The pull request's runs, and the app's stored comments, read from the database just before the post, can be read. Else `record_unreadable`.
3. Every file is reviewed and scored at this head, by this review or an earlier one, and none is listed as not reviewed (condition 2). Else `not_covered`.
4. The review's verdict says no person is needed, and its highest score and every file's final score are below the threshold in force now, whatever threshold the review was scored with (condition 3). Else `needs_human`.
5. This review has no major or blocker finding: on the diff, not placed on it, or on code unchanged since the last review (condition 4). Else `blocking_finding`.
6. No run of the pull request, published and not a dry run, nor this one, left a major or blocker finding without a thread that a later review can clear: one not placed on the diff, the placed ones of a review posted without its inline comments, one on code unchanged since the review before, or one dropped as a repeat of a thread that was closed for approval when it was dropped (for a finding stored before this release, of a thread that was settled) (condition 4). Else `finding_without_thread`, for as long as the pull request is open.
7. The pull request, as GitHub answered it at step 1, is not a draft (condition 5): else `draft`. Its branch is in the repository itself (condition 7): `from_fork` for a fork, and `origin_unknown` when GitHub's answer does not tell.
8. No major or blocker thread of the app's own is open under the thread rule (condition 4), read from GitHub's review threads now: a list that cannot be read is `threads_unreadable`, with its code; a thread open, or a lost one (below), is `open_thread`.
9. The base branch dismisses stale approvals (condition 8): `rule_off` when it does not, and `rule_unreadable`, with the read's code, when that could not be read.
10. The pull request is not drawn for the audit sample (condition 6): else `audit_sample` (see "The audit sample (condition 6)" below).

Condition 6, the audit sample, is read last, once every other condition holds, so a pull request drawn is one the service would otherwise have approved: by then its runs and stored comments, its threads and the base branch's rule have been read as for an approval, and the draw itself reads nothing. A stored result that cannot be read at any step is `record_unreadable`, never approvable. Each step is decided only when the ones before it held, and the review's paragraph names the first that failed, in this order: a person who fixes it may meet the next one only at the next review. GitHub is read in the same order: the threads only when steps 1 to 7 held, the rule only when step 8 did; the draw is made only when step 9 did. The database is read sooner: the runs and the stored comments of step 2 are read at every publication with approval on, before the pull request is read for step 1, so also for one that then ends `closed` or `head_moved`, one held for the wait after a failed post, and one that adopts a review already posted.

**Which threads hold it back.** Only the app's own threads count: a thread whose first comment is the app's, with the severity stored for that comment, major or blocker. A thread whose first comment has no stored row counts as one of unknown severity, as for the gate; minors and notes never count. A person is an account that is neither the app nor a bot. Access is what GitHub reports for each comment of the thread (`authorAssociation`): `OWNER`, `MEMBER` or `COLLABORATOR`; any other word, or none, is no access. The service looks up nothing more.

- **`strict`, the default.** A thread is closed for approval in two cases. (1) This review kept a `fixed` verdict for it, on a file that changed since the thread was opened, and nobody but the app wrote in the thread after the replies the review judged. (2) The thread is resolved, and either the app resolved it and the newest verdict a published review kept for it is `fixed` on a changed file, or a person other than the pull request's author (letter case aside), with access, replied in it. When that newest verdict is `open`, only a reply written after the comments that review judged counts; when the review did not record how many it judged, or its entry cannot be read, no reply counts. The app's own thread with no stored finding closes only by such a reply and a resolve.
- **`gate`.** A thread is open when the merge gate's rule, with this review as the head's review and the repository's `clearByReply`, would block it (see [The merge gate](merge-gate.md)), whether or not the gate is on.
- **Under both.** A thread this review kept `open` is open, even when it is resolved and a member replied. A lost thread is open: a stored major or blocker finding of a published run that is not a dry run, whose comment is not the first comment of a thread GitHub lists as the app's own (the comment was deleted, or the thread's first comment is no longer the app's), counts once; so does a stored row whose severity is unknown, or whose run is not among those read. A thread, a comment or a run that cannot be read counts as open.
- **Settled before a review.** With approval on, a thread is settled, and so not judged again (see "Earlier threads" under [Leaving dry run](leave-dry-run.md)), only when the rule described there and the thread rule both accept it: under `strict`, case 2 above; under `gate`, the app's resolve after a `fixed` or `answered` verdict, or, with `clearByReply` on, a person's reply and a resolve. So under `strict` a thread the author replied to and resolved is judged again by every review, and under `gate` with `clearByReply` off a thread a person replied to and resolved is judged again, also on a pull request that is not gated. A verdict can then close it.
- **What the rules cost.** More threads are judged at each review, and their files read. Under `strict`: a wrong finding costs one person's look, since the bot does not approve; a thread the app resolved after an `answered` verdict is judged again at every review until someone with access who is not the author replies, and, with the gate on, a new `open` verdict on it can make it block the gate again; a thread whose fix a review of an older head verified, and that nobody resolved, holds approval until a review of the present head verifies it again; and a member who replied before a review kept the thread open must reply again after it, or a review must verify a fix. Under `gate`: the author alone can close a thread, by a reply the review accepts or, with `clearByReply` on, by a reply and a resolve; and a thread a person replied to and resolved, that this review judged `open`, holds approval though the gate lets the merge through. Under both: a finding whose comment anyone deleted, or whose thread GitHub no longer lists as the app's, holds approval for the rest of the pull request, and a person reviews it instead.

**The base branch's rule (condition 8).** It is read last of what is read, before the draw alone, for the base branch GitHub names at the post.

- First `GET /repos/<owner>/<repo>/rules/branches/<branch>`: the rules of every ruleset that applies to the branch, 100 to a page, at most 10 pages. An entry of type `pull_request` whose `parameters.dismiss_stale_reviews_on_push` is `true` means the rule is on, and nothing more is read. Every entry is checked first: one that is not an object with a type, or a list that fills its tenth page, makes the list no answer, whatever its other entries say.
- Else `GET /repos/<owner>/<repo>/branches/<branch>/protection`: `required_pull_request_reviews.dismiss_stale_reviews` `true` means the rule is on; any other answer of 200, and a 404 (no protection), mean it is not.
- Either read saying so is enough. Both read and neither saying so is `rule_off`. One that could not be read, while the other does not say so, is `rule_unreadable`, with the first failure's code (the rules read's, when both failed). Every other answer of either read is a failure, a 403 included, whatever GitHub's message says. A server error, or no answer, is tried once more. The branch's name is sent encoded, a slash as `%2F`; an empty name, `.`, `..` and a name that cannot be encoded are refused before any request (`github_bad_path`).
- GitHub's permissions page lists the rules read under `Metadata` read, which every app has, and the protection read under `Administration` read.

**The audit sample (condition 6).** Of the pull requests the service would approve, a share is sent to a person anyway, so that people keep checking what it approves. It is read last (step 10), when every other condition held.

- **The share.** `auditShare`: a number from 0 to 100, a fraction such as 37.5 included, 5 when not written, under `repositories.defaults.score` for every repository and under `repositories.overrides.<owner/name>.score` for one, each replacing the default's. It is read with the other settings when the review is about to be posted. At 0 nothing is drawn, and no key is read.
- **The draw.** HMAC-SHA-256, keyed with the audit key's characters as the variable holds them, in UTF-8, over the pull request as the service stores it, in UTF-8: the JSON of the git service, the owner and the repository in lower case, and the number, such as `["github","acme","shop",7]`. The first four bytes of the digest, read big-endian as a number `u` below 2^32, draw the pull request exactly when `u * 100 < share * 2^32`. Both sides are exact, so a share is drawn as written, with no rounding: at 0 nothing, at 100 everything. The draw reads no head, no base branch and no time, and makes no request and no model call.
- **Every head.** What the draw is made over holds no head, so a pull request drawn is drawn again at every head at which every other condition holds, until the share or the key changes: pushing again does not draw it again. A new pull request for the same change is a new draw; that gap is accepted. Beside it, once one head of a pull request is approved or audited, its author knows how every later head of it will draw, until the share or the key changes.
- **The share or the key changed.** Draws nest: a pull request drawn at a share is drawn at every higher one, so raising the share only adds pull requests to the sample, and lowering it only takes some out. A change takes effect at each pull request's next publication; nothing is withdrawn or posted because of it alone. A new key draws every pull request again at its next review, unrelated to the old draw. A rename or a transfer of the repository that changes more than letter case changes the owner or the name the draw is made over, so it draws each of its open pull requests again at its next publication. Cost: an approval posted before a raise stands until the pull request's next push or review; a pull request a lower share no longer draws can be approved at its next review, but a push that tells nothing new after an audited review still ends `nothing_new`, since the newest review was no approval (see "A push that tells nothing new, after an approval" below), so it waits for a push with something new, or for `/review`.
- **The paragraph.** The review of a pull request drawn is posted as a comment, as any review that does not approve, and ends with the `audit_sample` paragraph (below), the same under both thread rules and with no code. It does not start with the word audit, and it says that every other condition holds: it tells the author that the pull request would otherwise have been approved, which makes the gap of a new pull request easy to see.
- **The record and the log.** The review is recorded with `approved` false and `approval_code` `audit_sample`, and its `review` line carries `approved: false` and `approval: 'audit_sample'`. Nothing records the share or the key that drew it, and the line does not carry the share. The draw gives out only whether the pull request is drawn: the key, the digest and `u` are in no log line, record, review, issue or alert.
- **What the rest does.** An audited review is a review that does not approve: after its publication the job asks for a withdraw job when the pull request has a standing approval, and that job withdraws it (see "Withdrawal" below). An earlier approval can be standing then only when the share or the key changed since it was posted. After a rename or a transfer of the repository that changes more than letter case, the service's records stay under the old name, so the service does not see an approval posted before it: that approval stands until GitHub's own rule dismisses it at a push, or a person dismisses it. The merge gate does not read the decision, and neither does receiving.
- **In dry run** nothing is decided, so nothing is drawn.
- **What it costs.** A pull request drawn has had its runs and stored comments read from the database, and its threads and the base branch's rule from GitHub, as one that is approved, and it is not approved. A condition that fails before the draw is named instead of it, so a pull request drawn at a head where another condition fails says only that reason. Nothing on GitHub marks an audited pull request: no label, no requested reviewer, no assignee, no check, no alert and no new permission. A person finds one by reading the review, or with the statement below. Nothing makes a person review it but the repository's own rule that requires an approving review, as for any review that does not approve (see "Require an approving review there too" above).

```sql
-- the reviews drawn for the audit sample, newest first
select id, number, head_sha, published_at from visto_ai.review_runs
where owner = 'acme' and repo = 'shop' and published and approval_code = 'audit_sample' order by id desc;
```

An audit is told from its code only. An audited review that a later start adopts (posted, then not recorded, then found on GitHub as a comment) is stored, as every adopted comment is, with `approval_code` null, and logged with no `approval`, so it is not told from a comment and the statement above does not list it.

**The paragraph.** With approval on, every review the service posts ends with one paragraph, after the `Overall` line and inside the end of the body that is kept when a body is cut to GitHub's size. With approval off the body is what it was. Below, `<commit>` is the first 12 characters of the reviewed head, `<threshold>` the threshold in force, and `<code>` a short code (`internal_error` when the code is not one). The first line is the approval; every other paragraph is `**Not approved automatically:**`, a space, and the sentence of its code:

```text
approved:               **Approved automatically** for commit `<commit>`: every file is reviewed, nothing is at or above <threshold>%, and no major or blocker finding is open. A new commit withdraws this approval.
record_unreadable:      a stored review of this pull request could not be read.
not_covered:            not every file of this pull request is reviewed and scored at this commit.
needs_human:            a part of this change is at or above <threshold>%, so a person should review it.
blocking_finding:       this review has a major or blocker finding.
finding_without_thread: a review of this pull request raised a major or blocker finding that no later review can clear: one not placed on the diff, one whose inline comment GitHub refused, one on code unchanged since an earlier review, or one that repeats a thread already closed. It holds approval for as long as the pull request is open.
draft:                  this pull request is a draft.
from_fork:              its branch is in a fork, and a pull request from a fork is never approved automatically.
origin_unknown:         the reviewer could not tell whether its branch is in this repository.
threads_unreadable:     the review threads of this pull request could not be read (`<code>`).
open_thread, strict:    a major or blocker thread of this reviewer is still open, or its comment is gone. Here a thread counts as closed when a review verified a fix in changed code, or when it is resolved and someone other than the author, with access to the repository, replied in it.
open_thread, gate:      a major or blocker thread of this reviewer is still open, or its comment is gone.
rule_unreadable:        the reviewer could not read whether the base branch dismisses an approval when new commits are pushed (`<code>`).
rule_off:               the base branch does not dismiss an approval when new commits are pushed. The reviewer approves only where a ruleset or the branch protection of the base branch dismisses stale approvals.
audit_sample:           this pull request was drawn for the audit sample. Every other condition for an automatic approval holds, and a share of the pull requests this reviewer would approve is sent to a person anyway, so that people keep checking what it approves. A person should review it.
refused:                GitHub refused this review as an approval (`<code>`), so it was posted as a comment.
```

Only one reason is given. A body the service cannot write again from the stored result is posted as it was recorded, with the paragraph decided now after it, and the decision stands. The decision's code is stored in `review_runs.approval_code`, and the `review` log line carries `approved` and `approval` (the code, or null for an adopted approval) only when the publication made a decision or adopted an approval.

**A refused approval.** An approval is sent once. When GitHub refuses it (`review_rejected`), the decision becomes `refused`: the same review, with its inline comments, is posted once more as a comment that ends with the `refused` paragraph; if GitHub refuses that too, it is posted as with approval off (without the notes, then with the body written whole), all as comments. Any other failure of the approval's post is a failed publication, as for a comment: the review stays recorded, and the later start, 15 minutes on, asks GitHub for the app's own reviews first and otherwise decides again. Cost: when GitHub refused an inline comment and not the approval, that head is not approved.

**What is recorded.** Each published review records whether it was posted as an approval (`approved`) and the decision (`approval_code`). An approval also records when it was dismissed (`dismissed_at`) and by whom (`dismissed_by`: `app`, or `git_service` for one GitHub already held as dismissed, or no longer as an approval), the code of a withdrawal that failed while it stands (`dismiss_failure`), and when it still stood at a merge though it no longer held (`stood_at_merge`, see "A merge under a stale approval" below). Every review recorded before this release reads as no approval. To read them (with `docker compose exec db psql -U postgres -d visto`):

```sql
-- approvals of the app's own that are not known as dismissed
select id, number, head_sha, review_id, approval_code, dismiss_failure, stood_at_merge from visto_ai.review_runs
where owner = 'acme' and repo = 'shop' and approved and dismissed_at is null order by id desc;
-- why the reviews of a pull request did or did not approve
select id, head_sha, published_at, approved, approval_code, dismissed_at, dismissed_by from visto_ai.review_runs
where owner = 'acme' and repo = 'shop' and number = 7 and published order by id;
```

**Withdrawal.** A standing approval is a review of the app's own posted as an approval, recorded as published, not in dry run, and not recorded as dismissed.

- **When it is asked for.** A withdraw job is stored for a pull request with a standing approval: in the delivery's transaction, on a push, a retarget, a reopening and a merge, whatever the review filters say (a draft, an ignored author, a filtered base branch, the gate); on a `pull_request_review` delivery of action `dismissed` that names one of these approvals; in the transaction that records each publication of the pull request, the approving one included; when a start finds that GitHub holds as an approval a recorded review of a commit other than the live head; and at start, out of dry run, after the gate's sweep and before listening, for each pull request stored as open whose standing approval carries a failed withdrawal (logged as `withdraw_sweep`, with the count, only when it asks for one). Each is due at once. In dry run none is stored.
- **The lane.** Withdraw jobs run in a lane of their own, of 2 places, which is never paused, by the daily limit or by the model's key. A pull request has at most one waiting: another ask moves its time to now and keeps its starts.
- **What a job does.** It reads the pull request from GitHub. On an open one it withdraws each standing approval whose head or base branch is not the live one, and every standing approval when the newest published review of the pull request is not an approval that stands. For each, it first reads the review: one GitHub holds as dismissed, or no longer as an approval, is recorded as dismissed by the git service, and nothing is sent; one it holds as approved is dismissed with the message below and recorded as dismissed by the app. When the dismissal fails, the review is read once more, and dismissed then is no failure. A review GitHub does not find is a failure (`review_not_found`), never a dismissal, and so is one in another state (`review_state_other`). On an open pull request every other standing approval is read too, once at each start of a job: one that carries a recorded failure as told below; any other, one that needs no withdrawal, is recorded as dismissed by the git service when GitHub holds it as dismissed, or no longer as an approval (by GitHub's own rule or by hand), and on a gated pull request the check is then asked for again, as after any dismissal; one GitHub holds as approved is left as it is; and a read that fails, a review GitHub does not find and one in another state change nothing and are no failure: nothing is recorded on it, and the job is not tried again for it. A closed pull request, and one GitHub does not find, are left as they are. With no standing approval the job ends `none`, with no installation known `no_installation`, and when it withdrew nothing, had no recorded failure to read and recorded nothing, `kept`. The message: `This approval was for commit <commit>. A new commit, a change of the base branch, or a later review of this reviewer that does not approve means it no longer holds.`
- **When it fails.** A job that fails is tried again after 10 seconds, then after 60. At its third start that fails, before it ends, it records the failure's code on each approval it could not dismiss and, when it could not read the pull request at that start, on every standing approval, with that read's code. When one of these is recorded for the first time, or cannot be recorded, it raises `dismissal_failed` once (with `reason`, `repo` and `number`) and asks for the gate's check. A withdraw job the runner drops, because it is a day old (`too_old`) or out of starts (`attempts_exhausted`), records that reason on every standing approval of its pull request; it raises `dismissal_failed` with it when one of these is recorded for the first time or cannot be recorded (so not for a pull request with no standing approval, nor for one whose standing approvals all carried a failure already), and, out of dry run where the repository's gate is enabled, asks for the check. Out of dry run, a job dropped as `too_old` is also asked for again at once, as a new job: its re-check, on an open pull request, withdraws the approvals that no longer hold and clears the failure of those GitHub still holds as approved; on a merged one the targets are recorded as standing at the merge (`stood_at_merge`), and a recorded failure on an approval that is not a target stays. One dropped as `attempts_exhausted` is not, since a crash that repeats would loop. Each start logs its own `withdraw` line; a job the runner drops logs the runner's `job` line instead (see "The log" below). No timer tries a failed withdrawal again: the next push, retarget, reopening, publication, dismissed review or start of the service does.
- **The check.** On a gated pull request, the gate's check of the live head, whichever head that is, then fails for as long as a standing approval carries a recorded failure: completed, `failure`, titled `Earlier approval not withdrawn (<code>)`, whatever a skip or a review says; only `bypass` passes it. A recorded code that is not a short code shows `internal_error`. When the recorded failures cannot be read, the evaluation fails as when the skip cannot be read: it is tried again, then raises `gate_check_failed`. The check's summary:

```text
This reviewer approved an earlier commit of this pull request, or gave an approval it no longer stands behind, and could not dismiss it (`<code>`). While it stands it may count toward the approvals this branch requires, so this check fails.
Dismiss that approval on the pull request's page. The service also tries again at the next commit, the next review of this pull request and its next start, and this check is decided again once the approval is gone.
```

- **How a recorded failure ends.** When a later withdraw job finds that approval dismissed, by the app, by GitHub's own rule or by hand, it is recorded as dismissed. On an open pull request a job also reads each standing approval with a recorded failure that it does not withdraw (one at the live head and base, while the newest published review is an approval that stands): one GitHub holds as approved has its failure cleared, and is never dismissed this way. Either way the check is then asked for again. A read that fails keeps the failure, with no new alert.
- **A later review of the same head that does not approve** withdraws the earlier approval of that head. Cost: a re-check whose thread read or rule read fails takes back an approval that was right, and where GitHub refuses the app's dismissal and no push follows, it becomes a failed withdrawal, with its alert and, under the gate, a failing check.
- **A draft.** A conversion to draft asks for nothing: the draft keeps the bot's approval. A push while it is a draft asks for a withdrawal as any push does.
- **A merge under a stale approval.** On a merge's delivery the job reads the standing approvals it would withdraw on an open pull request: each one whose head or base branch is not the merged pull request's, and every one when the newest published review of the pull request is not an approval that stands (a dismissed newest approval counts too). One GitHub still holds as approved is recorded as having stood at the merge (`stood_at_merge`) and raises `stale_approval_merged` (with `repo` and `number`), once; one it holds as dismissed, or no longer as an approval, is recorded as dismissed by the git service; one GitHub does not find is left as it is, and so is an approval of the merged head and base while the newest published review is an approval that stands. None is dismissed after a merge. A read of a review that fails three times records and alerts nothing. Cost: an approval a person dismissed after the merge reads as never having stood.
- **The log.** One `withdraw` line for each start of a job, so a job put back twice logs three: the job, the repository, the number, the live state, the counts `standing`, `targets` (the approvals it withdraws, or reads at a merge), `dismissed`, `by_git_service` and `failed`, the first failure's code, the outcome, and whether it was put back. `dismissed` and `by_git_service` count only the approvals this start's own records changed. A job the runner drops logs no `withdraw` line: the runner's own `job` line says `dropped`, with its reason, and `dismissal_failed` is raised as told under "When it fails". An `accepted` line carries `withdraw: true` when its delivery asked for a job. No line holds a login, a branch, a path or a message.

**A push that tells nothing new, after an approval.** With approval on, a push's review that would end `nothing_new` (see "Reviews after the first" under [Leaving dry run](leave-dry-run.md)) is recorded, posted and decided when the newest published review of the pull request was posted as an approval, dismissed since or not: an approval belongs to one head, and the new head needs its own. Its scores are stored as any recorded review's are. When that read of the newest review fails, the review is posted as a comment whose paragraph gives `record_unreadable`. A push to a head whose review is the newest published one still ends `already_reviewed`. Cost: one more review in the pull request for each such push, with no model call; a head that comes back to the newest review's head after its approval was withdrawn stays unapproved until `/review`.

**Resumed and adopted reviews.** A recorded review that a later start posts is decided at its post like any other. One that another job recorded keeps the text it was recorded with: its body is the recorded one, followed with approval on by the paragraph decided now, and, when GitHub refuses its inline comments, the body written whole keeps that job's trigger and names no requester, with approval on or off. A review the service finds already posted (see "Asked first" under [Leaving dry run](leave-dry-run.md)) is not decided again: when GitHub holds it as an approval, or as dismissed (only an approval can be dismissed there), it is recorded as an approval with no decision code and, when dismissed, as dismissed by the git service; for an approval found at another commit than the live head, not dismissed, a withdrawal is asked for. A review of the app's own whose commit GitHub gives as none (a commit pushed away and collected) is not listed, so it is never adopted. Cost: the stored body of an adopted approval lacks the paragraph GitHub's copy has; the body written whole of a `/review` another job recorded says it was requested and names nobody.

**The event.** GitHub's `pull_request_review` delivery of action `dismissed`, an event the app already needs, is read: it stores nothing of its own, and asks for a withdraw job when it names a standing approval of the app's own. So while the pull request is open, a dismissal by GitHub's own rule or by hand is recorded, and on a gated pull request the check asked for again, seconds after GitHub delivers it: the job reads every standing approval (see "What a job does" above). Once it is merged, only the approvals a merge reads are read (see "A merge under a stale approval" above), so the dismissal of an approval of the merged head and base, while the newest published review is an approval that stands, is not recorded; once it is closed, none is read. With approval off it is recorded as handled, where it was ignored as `unknown_action`.

**In dry run** nothing is decided, nothing is posted as an approval, no withdraw job is stored, and one found is dropped as `dry_run`; every call that reads the rule, reads a review or dismisses one is refused.

**What it costs.**

- Every publication with approval on makes two more reads of the database (the runs and the stored comments), before it reads the pull request and whether or not it then posts. One that gets to step 8 reads the review threads: one request for each 100 threads, and one more for each 100 comments of a thread past its first 50. One that gets to step 9 reads the rule: the rules list, one request for each 100 rules, up to 10, then, when the list does not say the rule is on, the branch protection; a server error, or no answer, is tried once more.
- A pull request drawn for the audit sample (step 10) has made every read above, the threads and the rule included, as one that is approved, and is posted as a comment. The draw itself makes no read and no request.
- A push that lands between the read of the pull request and the post leaves an approval on the commit that was read; the publication's withdraw job reads the live head and dismisses it, so such an approval can stand for a few seconds on a head it was not decided for.
- A withdraw job runs after each publication on a pull request with a standing approval, the approving one included, and usually finds nothing to do. Each start reads the pull request and, on an open one, every standing approval: one read of GitHub for each standing approval at each start of a withdraw job, so the job after an approving publication reads that approval once; an approval withdrawn takes two or three calls.
- Every review of a repository with approval on carries one more paragraph.
- An extension module's notifier is told of an approval, and of an audited review, as of any published review: the notice has no field that tells them apart but its body's last paragraph, which the body of an adopted review lacks.
- With approval off too: out of dry run, every delivery of a push, a retarget, a reopening, a merge and a dismissed review reads `review_runs` once in its transaction, and so do each publication, each start and each gate evaluation; the withdraw lane looks for due jobs with the other lanes; the state of the app's listed reviews and the access of thread comments are read and not stored; a review GitHub holds as an approval, found already posted, is recorded as one; a review another job recorded, when GitHub refuses its inline comments, is written whole naming no requester.

**The migration.** Automatic approval adds one migration, `0013_approval`: six columns of `review_runs` and one index. It is applied once, and every row stored before it reads as no approval. A previous release finds a migration it does not know and refuses to start on that database, so it cannot be put back.

**What was tried.**

- **Against a real GitHub App, on a private scratch repository.** GitHub names the app's permission `administration` with `read`. The thread query with `authorAssociation` is accepted: a member's reply reads `member`, and the app's own comments `none`. Both reads of the rule answer 403 on a private repository whose plan holds neither rulesets nor branch protection, for any branch, one that does not exist included: so the reviewer cannot approve there, and says `rule_unreadable` with that code. One review through the service with approval on was posted as a comment ending with that paragraph, and its run stored the code. Through the adapters, an approval posted with the event `APPROVE` was listed and read as approved, dismissed, then read and listed as dismissed. A second dismissal of the same review answers 422, which the withdrawal's read after a failed dismissal treats as no failure.
- **Under Docker, in a network with no way out, on a real Postgres.** The migration over the previous release's database: the rows stored before read as no approval, and the previous release then refuses to start. A push of a gated pull request with a standing approval: a withdraw job stored in the delivery, its retries, its give-up with the failure recorded, one alert and the gate asked, and the start's sweep asking again. A withdraw job older than a day dropped, recorded and alerted. Every statement of the record and of the lane.
- **The audit sample.** Under Docker, in a network with no way out, on a real Postgres: the previous release and this one start on the same database (no migration); a missing, unset or short key refuses the start with its issue and no value, in dry run too, and the eval command refuses the same way; a key long enough starts, a share of 0 needs no key, inside the image the draw gives the tests' values, and no key is in any log. Not tried against GitHub: no review on the scratch repository gets past `rule_unreadable`, so none reaches the draw.
- **Not tried.** An approval decided and posted by the service, and an audited review posted by it: they need a repository whose rules dismiss stale approvals, a public one or one on a plan that holds rules. A merge under a standing approval. GitHub's own deliveries: the scratch app has no webhook, so neither GitHub's own dismissal on a push nor a `dismissed` delivery was seen. A pull request from a fork. How a slash in a branch name is taken by the two reads. The run under Docker came before the last fixes, so a withdraw job dropped as `too_old` being asked for again, and the alert of a drop raised only for a new failure, were not run there.
