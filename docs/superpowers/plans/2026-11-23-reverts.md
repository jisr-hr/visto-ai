# Reverts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A deployment remembers which changes had to be taken back. Every pull request event already carries the pull request's description; the service now reads its first line that is not blank, and when that line is the one GitHub's revert button writes, `Reverts <owner>/<name>#<number>`, it stores the number, whether or not learning is on. With learning on, when the reverting pull request is merged, the learning pass records the files of the pull request it reverted: one record of the kind `revert` for each path, dated by the merge of the revert, live for 180 days. Later reviews of the same repository are told, as context for the score, that a change to a file they touch was reverted: one line for a file, with its path, a day and the word `reverted`, under a rule of its own that is shown only with such a line. A reverted line holds nothing a person wrote. It sets no score, no floor, no finding and no gate. It never costs a review a signal: it stands after the signals' lines, takes none of their places, and is the first thing left out when the lines or the room run short. It is shown neither to the pull request that made the revert nor to the one that was reverted, and not at all where a second scorer is named. The score backtest's memory makes the same records from a history file, as of each case, and its free count says how many cases would be shown one. No model is called, no key is added to the config, and the git service is not read. With `learning` not written, the service does what it does today but for one stored number.

**Architecture:** The places the two plans before used. `src/memory/reverts.ts` is new and pure, by the lint as it is: the one rule that reads a revert's reference out of a description, the one reader of a stored review's files, and the one rule that turns a revert into records. The GitHub event parser, the learning pass and the eval all import it, so the webhook, the database and a history file cannot disagree. `src/db/` holds one migration and the statements. The parser (`src/forge/github/events.ts`) puts the number in the facts of a pull request event, and the statement that already stores those facts stores it. In the shell, `src/shell/learning.ts` makes the records inside the transaction it already opens for a pull request, and `src/shell/memory.ts` reads them for a review. `src/memory/select.ts` chooses the signals' lines as it did and adds the reverted lines after them, `src/engine/context/memory.ts` checks a reverted line and prints it, and `chooseMemory` in `src/engine/review.ts` tries memory without its reverted lines before it gives up for room. `src/eval/backtest/memory.ts` makes the same records from a history file.

**Tech Stack:** Unchanged. No new library. One migration, `0012_reverts`: two columns.

**Spec:** `docs/superpowers/specs/2026-11-13-visto-ai-design.md`. Executors read both. Section numbers below refer to it: 3 (G4, G5, O10, O11, D8, D13, D14, D19, D23, D25); 5.1; 5.3 (memory blocks); 5.4 (the rules for memory); 6.2 (D8); 6.5 (reverts); 6.6 (who makes a record, the backtest); 6.7; 7 whole; 8.1; 10; 11.1; 13; 14; 15; 16; 18 (stage 8); 19; 20; 22.

**Notes:** the notes file beside this plan is written when the build ends. This is the third plan of stage 8 and the first of two for what the lessons plan left (call 1). The plan after this one holds the evals with lessons and the measurement: a date for each case of the findings replay; a file of the reviewer's own findings, the replies under them and the later reviews' verdicts, written from a deployment's database; the judge's nightly rules (the day window, the bounds of 100 and 20, the cap of ten, the attempts) moved out of the shell into `src/memory/` unchanged; lessons made from that file night by night by that code and kept in a file, so a second replay pays nothing; the replay and the backtest shown those lessons as of each case; block scores in the replay's results; and the comparison with and without lessons, with the blocks and pull requests that cross each threshold downward against the same count between two runs without lessons.

**This plan was reviewed before it was built.** The review ran every statement and the migration on the in-process Postgres and found nothing critical, four important points and eleven minor; all were ruled on by the session lead and are applied here: a test that contradicted the rule on the cut of a description (Task 1); a reference a person who merges never sees, in a comment or a collapsed block, now closed by reading the first line alone (call 2); a reference set after the merge when deliveries arrive out of order (call 3); the design's sentence on who may make a record (Task 9); and, because nothing learned may lower a score, a reverted line that could take a signal's place among the lines or cost memory its room (calls 12, 14 and 17).

**Words used below.** *Revert*: a merged pull request whose description's first line that is not blank named an earlier pull request of its repository, in the form the revert button writes. *Reverting pull request*: the one that carries the line. *Reverted pull request*: the one the line names. *Reference*: that line. *The merge's delivery*: the `closed` event of a pull request that is merged. *Record of a revert*: one row of `memory_records` of the kind `revert`, for one path of the reverted pull request. *Reverted line*: a line of the pull request block made from such a record. *Signal's line*: any other line of that block. *Signal*, *live at a time*, *as of*, *the day*, *printable*, *changed file*, *near*, *pass*, *the header message*, *short code*, *person with access*: as in the two plans before. *Merge time*: for a pull request stored as merged, its close time as the pass already reads it, `coalesce(closed_at, merged_at, updated_at)`; for a case of a history file, its `merged_at`. *Completed run*: a row of `review_runs` whose outcome is `ok`, a dry run included.

**How a revert is recognised**

2. **(builder) No model, no config key, no read of the git service. From the description alone. (ruled after the review) From its first line alone.** Only the first line of a description that is not blank counts, and it must begin, at its first character, `Reverts <owner>/<name>#<number>`: what GitHub's revert button writes as the description of the pull request it opens. The owner and the name must be the pull request's own repository. So a reference inside an HTML comment, a collapsed `<details>`, a fenced or an indented block, a quote, or on any later line is no revert: the line that counts is the one a person who merges sees at the top. Only the first 4,000 characters of a description are read, which is what a history file keeps of one, so the service and a file see the same text; a reference that ends at the last of them is not read, since the cut may have shortened its number. **The design is wider:** 6.5 says "description or commit messages", and a reference "to its merge commit". Cost: a revert made on the command line, whose reference is a commit in a commit message, is not recorded; neither is one whose author put a sentence, a template or a space above or before the button's line, wrote the short form `Reverts #12`, or whose repository was renamed since. The form is taken from how the button is known to behave, not from a payload read while planning (To verify, item 1; Task 9, rule 5).
3. **How surely: the line is the author's, and the merge is what vouches for it (ruled after the review: by the visible first line, and by the merge's own delivery).** Anyone who opens a pull request can write the line, a stranger on a fork included. Two things stand against that. Only a pull request stored as **merged** makes a record, which takes a person with write access, and the line they merged is the first one shown, never a hidden one (call 2). And once a pull request is merged, what it reverts is taken from **the merge's delivery alone**: an event of a merged pull request that is not its `closed` one, such as an edit after the merge, never sets the number, in whatever order the deliveries arrive. Without that, the author of any merged pull request could add the line afterwards and mark another pull request's files. **The design is narrower on who makes a record:** 6.6 says a record of memory "is made only from a comment by a person with access"; a record of a revert is made from a merge, of a pull request whose description's first line names the one it reverts, and the description's author may have no access. Cost: a first line that names a pull request it does not revert, merged by a person who did not notice, records that pull request's files, and the only bound is what a reverted line can do (call 17); a true reference added after the merge is lost; when the merge's delivery is lost, or arrives after a later event of the merged pull request and is refused as older, the number is what the last event before the merge named; a pull request the service first hears of after its merge, by another event than its merge, has none.
4. **From the events the service already receives, with no new subscription.** GitHub sends the description with every `pull_request` event. The parser reads the number from each event of a pull request that is not merged, and from the merge's delivery; an `edited` event stays the action `other`, queues nothing, and is stored like any other. Nothing else of a description leaves the parser: no word of it is stored, logged or sent. Cost: a deployment that never receives the merge's delivery, and gets no redelivery of it, records the revert only if an earlier event already named it, and nothing if the pull request is never stored as merged.
5. **(builder) Capture is not learning.** 7.1 lists reverts under what is captured from the first webhook. With `learning` not written, exactly one thing changes: the statement that already stores a pull request also stores the number. No other row, no log line, no model call, no timer; nothing reads the number. A deployment that switches learning on later has its reverts made by the first passes, each dated by its own merge. The pin is Task 3's `with learning off a merged pull request that names a revert stores the number and nothing else`.
6. **At the merge, not nightly.** The pass that makes signals already looks once at every pull request that closes, in a transaction of its own, woken by the close's delivery. A revert is recorded there. **The design says "recognised nightly"**, which it needed for a read of the git service that this plan does not make. Cost: one more read for every pull request a pass looks at; for a merged one that names a revert, one more read and, when it records, one insert.

**What is recorded**

7. **The files are those of the reverted pull request's last review:** the newest completed run, a dry run included, whose stored list of files is not empty; of each file only its path and, for a renamed file, its old path are read. It is the one place the service holds a pull request's files. With no such run nothing is recorded, and the pass says `no_files`. Cost: a pull request the service never reviewed is not recorded as reverted: one merged before the app was installed, a draft, an ignored author, a filtered base branch, a gated pull request nobody asked a review of. The files are those of the last head a run read, so a file added after it is missing. And a run whose file list was cut by the git service's own limit holds what it was given.
8. **Three guards, and no retry.** A record is made only when the reverted pull request is stored, is stored as merged with a merge time at or before the merge of the revert, and is another pull request. Otherwise none is made and the pass says `not_stored`, `not_merged` or `same`. The reverting pull request is then marked as looked at, like any other. Cost: a revert whose reverted pull request the service does not store as merged when the pass looks is never recorded. That is so when that merge's delivery was lost, and just as much when it only arrives later: after an outage that covered both merges, redelivered in another order, the revert is looked at first, says `not_merged` or `not_stored`, and is not looked at again. The README gives the statement that has one looked at again.
9. **One record for each path.** Its source reference is `<reverting number>:reverts:<reverted number>:<path>`; its `number` is the reverting pull request's, which is the pull request it came from; a new column `reverted` holds the other. It has no category, no reason, no excerpt and no comment, and is never a miss. It is made at the merge time of the revert and expires 180 days after (7.2), from the data and never from the clock. At most 300 paths of one revert are recorded, in the stored order, and a path that is not printable makes none: it could never be shown. Cost: a revert of a larger pull request records its first 300 paths; one revert writes up to 300 rows.
10. **A partial revert and a revert of a revert are not told apart.** A revert that took back half of a pull request records every file of it: the service does not hold the reverting pull request's files reliably, since a revert is often merged before any review of it has run. A pull request that reverts a revert records the files once more, on its own day, and so do two reverts of one pull request. A file then has several records and still one line, the newest (call 12). Cost: a file a partial revert left alone is said to have been part of a change that was reverted, which is true of the change and not of the file; a change that was reverted and brought back reads the same as one that was only reverted.
11. **Every revert the pass looks at is one log line,** with the two numbers, a short code and two counts, after its transaction commits; its records count in the pass's `added`. A revert that is silently never recorded would look like no revert. Cost: the line is written again, with `added: 0`, whenever a later comment makes the pass look at that pull request again.

**What a review is shown**

12. **One reverted line for a changed file, beside the signals' lines and never in place of one (ruled after the review).** As first written a reverted line was chosen with the signals, newest first, so it could take one of a file's three places, or of the thirty, from a signal marked as a miss: something learned would then have removed context that raises a score. So the signals' lines are chosen exactly as before, as if no revert existed. Then, for each changed file, at most one reverted line: the newest revert of its path or of the path it had before a rename. It holds `changed`, the path in a code span, the day the revert was merged, `-`, and `reverted`. Every reverted line stands after every signal's line, and the limit of 30 is applied to the whole list, so what it cuts is reverted lines. No reverted line is `near`. Cost: an older revert of a file is not shown beside a newer one; with thirty signals' lines no reverted line is shown, and the audit counts it; a file near a reverted one is told nothing.
13. **No count in the repository block.** Its lists stay what its rule text says they are: where a person who was not the author commented. A review whose only line is a reverted one is still shown the lists. Cost: a directory where changes keep being reverted is not listed for it.
14. **A third rule text, shown only with a reverted line; the two that exist are not edited. And reverted lines are the first to give way for room (ruled after the review).** The text stands between the rules of the pull request block and the lines. So a review with no reverted line is sent the bytes it was sent before, and the contract test's two pins hold. Memory is still shown only when it costs the files nothing; when it does not fit with its reverted lines and their rule, the engine tries the same memory without them before it gives up with `no_room`, and the audit says that the reverted lines were cut. So the rule's 216 tokens can never cost a review its signals. Cost: about 216 tokens more in a review that shows a reverted line; one more packing of the files in a review whose memory fits only without them; the first paragraph still says that a line stands for a person's comment, and the paragraph after it says which lines do not.
15. **(builder) A reverted line tells nothing a person wrote:** a path, a day and a word of the service's own. The planner's part: a record of a revert is never shown to the pull request that made it nor to the one it reverted, by the shared code and by the read; a pull request that reverts a revert **is** shown that the change it brings back was reverted, which is the history of its files and not news of itself. Cost: none known.
16. **(builder) With a second scorer named, a reverted line is not shown,** as a signal is not: the review asks nothing of this part of memory there. Cost: such a deployment stores the records and shows none.
17. **D8, by structure (ruled after the review).** A record of a revert exists only to say that a change needed more attention than it got. No record argues the other way, and the engine gives a reverted line no category and no miss, whatever a memory hands over. No code path takes a record to `reconcileScores`, a floor, a finding or the gate. And a revert never costs a review a signal: not a place among the lines (call 12), not the room (call 14). What is left is the model: it could read a file with no line as safer, and the rule says not to. Only the backtest's moves across each threshold, against the noise, can show that, as for signals.
18. **Read on its own, once for a review.** The reverts live at the review's time are read after the signals, the newest 1,000, in a transaction with its own statement limit. They are not read again for the day's counts. Cost: one more read for every review with learning on; more than 1,000 live reverts leave the oldest out, and the audit says `memory_cut`, `records`.

**The data model**

19. **One migration, `0012_reverts`:** `pull_requests.reverts` and `memory_records.reverted`, both whole numbers that may be null. Every row stored before has null in both. The previous release, started on the migrated database, refuses to start, as after every migration. The seed command writes records through the statement that now writes the new column, so it asks for this migration where it asked for `0011_lessons`. Cost: a pull request merged before the upgrade is stored as merged with no number, and by call 3 stays so.

**The eval**

20. **The backtest's memory makes reverts from the memory file alone, by the two functions the service uses.** For each pull request of the file whose description names another one that the file holds, of the same repository and merged at or before it: records for that one's `final_files`, dated by the revert's `merged_at`. `--memory` is the option it was; no field is added to a history file, so the files that exist work. Cost: a revert shows only when both pull requests are in the file's window; a file knows every file of a pull request, so its reverts are fuller than a deployment's (call 7).
21. **A free count first, and no comparison of its own.** `eval:memory-count` gains one line: how many reverts the memory file names, how many it holds, and how many cases would be shown a reverted line; then one line for each such case. `eval:score-compare` is not changed: it compares memory as a whole. A paid run is made only when at least 10 cases would be shown a reverted line (Task 9, rule 6). Cost: with fewer, what a reverted line does to a score is not measured, which is the likely outcome on a history of a few dozen pull requests; and the comparison cannot tell a case shown a reverted line from one shown a signal's.
22. **The seed writes no record of a revert.** 7.5 lists the activity of people and the signals. Cost: a deployment seeded from a history file knows no revert from before its install.
23. **A case no person reviewed keeps its merge time as its date.** A history file holds no time of opening, and a revert is often such a case. The shared code keeps it from being shown its own revert. Cost: such a case is shown what was recorded between its opening and its merge, a little more than the service would have had.

## Global Constraints

Every constraint of the earlier plans still holds. The ones that bite most often, and the new ones:

- **Runtime and language:** Node 26 or later, npm, no build step. Erasable TypeScript only. Type imports use `import type`. Relative imports end in `.ts`.
- **ASCII only in source and tests.** A non-ASCII character is written as an escape. After each task the ASCII check of the plans before prints nothing (on macOS: `perl -ne 'print "$ARGV:$.:$_" if /[^\x00-\x7F]/'` over the files of `src`, `contract`, `test` and `examples`).
- **No test reaches the network, a real database or a model.** A database is `testDb()`. A model is a literal that records its requests. A memory in an engine test is a literal object. A clock is passed in.
- **Every wait in a new test has a bound.** A test that waits for the service uses the harness's `until`, which fails after 5 seconds; a test that waits for a promise wraps it in the file's own `bounded(work, 2_000)` or an equal of it. A wrong build fails; it does not hang.
- **With `learning` not written, one thing changes:** `pull_requests.reverts` is written by the statement that already stores the pull request. No row of another table, no log line, no timer, no model call, no alert. The pin is the service test of Task 3.
- **With no revert, every byte is what it is today.** A pull request event whose description names no revert parses to the object it parsed to, unless it is an event of a merged pull request other than its `closed` one, which gains one key. A lookup over a repository with no record of a revert returns the blocks it returned. export const REVERT_DESCRIPTION_CHARS = 4_000;   // of a description that are read: what a history file keeps of one

/** The pull request a description says it reverts: its first line that is not blank is the line the revert button writes, and names this repository. null when it names none. Total: never throws. */

  number: number;                    // the reverting pull request
  mergedAt: string | null;           // its merge time

**Rules (6.5, 7.2, calls 2, 8, 9):**

1. **What is read.** `revertedNumber` returns null for what is no string. Else the text is `stripControl(description).text` cut to its first `REVERT_DESCRIPTION_CHARS` characters, split at line feeds. A line is blank when it holds nothing but spaces and tabs. **Only the first line that is not blank counts:** no line after it is read, whatever it holds. With no such line, null.
2. **The reference.** That line must match `/^Reverts ([A-Za-z0-9_.-]{1,100})\/([A-Za-z0-9_.-]{1,100})#([1-9][0-9]{0,9})(?![A-Za-z0-9_])/` from its own first character, with no space or tab before the word: the word as the button writes it, one space, the repository, `#`, a number with no leading zero, and then the end of the line or any character that is no letter, digit or underscore. When `REVERT_DESCRIPTION_CHARS` characters were read and the match ends at the last of them, it names nothing: the cut may have shortened its number.
3. **Its own repository.** The owner and the name it holds must equal `repo.owner` and `repo.repo`, all four in lower case. The number must be at most 2,147,483,647. A first line that matches the form and fails either names nothing.
4. **So what is hidden or meant otherwise is no revert:** a reference on a later line, inside an HTML comment, a `<details>` block or a fenced block (each begins with other characters than the word), in an indented block, or after a quote mark or a list mark. None of them needs a rule of its own.
5. **`revertedFiles`.** `files` must be a list, else `[]`. An entry counts when it is an object whose `path` is a string that is not empty; its `previousPath` is kept when it is a string that is not empty, else it is null. Anything else is passed over. Nothing throws.
6. **`revertsOf`, in this order, the first that holds:** `reverted` equals `number`: `same`. `revertedStored` is false: `not_stored`. `readTime(mergedAt)` is null, `readTime(revertedMergedAt)` is null, or the second is later than the first: `not_merged`. No path is left by rule 7: `no_files`. Else `recorded`, with the records. Every code but `recorded` has no record.
7. **The paths.** For each file in the order given: its `path`, then its `previousPath` when that is not null. A path is taken when it matches `MEMORY_NAME` and was not taken before. The first `REVERT_FILES` taken are recorded; the rest are left out.
8. **A record.** `sourceRef` is `<number>:reverts:<reverted>:<path>`; `number` and `reverted` as given; `directory` is `directoryOf(path)`; `createdAt` is `mergedAt` written as a UTC ISO time; `expiresAt` is `REVERT_DAYS` days after it. The records are in the order of rule 7.
9. **Nothing here reads a clock, a database or a file.** The same input gives the same output.
